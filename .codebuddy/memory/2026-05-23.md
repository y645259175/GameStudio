## 17:43 ADR-0003 v3 重大重构 + 新增 ADR-0005 Buff 系统

### 用户审反馈（关键设计纠偏）

用户指出 ADR-0003 的核心设计错误：

### 新设计：三维度独立 + 通用 Buff 系统

| 维度 | 值 | 性质 |
|---|---|---|
| **Identity** 身份 | MASTER_CURRENT / DISCIPLE / ELDER / NON_SECT | 长期，互斥 |
| **ActionState** 行动状态 | IDLE / IN_CLOSED_DOOR / RECOVERING / DEFECTED / DEAD | 即时，每月可刷新，互斥 |
| **Buffs** 修饰器 | 由 BuffService 管理 | 可多个并存，不互斥 |

NonSect 身份是关键扩展——路人 / 敌人 / 异宗弟子共享 Character schema，未来通过 `non_sect_role: String` 子分类。

### 通用 Buff 系统（用户提出的重大架构）

设计要点：
- 大类（category）+ 小类（subtype）+ 时长（1~∞ 月）+ 自定义属性（每种 buff schema 独立）

### 这次重构的元教训（非常重要）

**维度混叠是设计常见错误**，特别在状态机设计：
- 把"身份" "行动状态" "临时修饰"塞一个 enum 看起来简洁，但语义错误
- 一个角色可以"是门主 + 在闭关 + 中毒中"，三个维度并存
- 强行用一个 enum 会失去叠加表达能力

**通用 buff 系统是 §6.9 解耦原则的最佳示例**：
- 把"临时修饰器"这个跨切面关注点提到通用层
- 每个系统注册自己的 buff 类型，而不是各自实现
- 月度 tick 集中处理，避免散落在各系统的 timer

**用户的设计直觉很强**：直接指出"维度有问题"+ 提出 buff 系统，比 AI 的"封闭式状态机"更通用、更未来友好。AI 应该更早识别这种"叠加状态"需求。

## 20:10 v3 撤离收益设计哲学纠偏（重要）

### 我的过度设计

我在撤离收益讨论里推荐了 C 方案：
- 配表 multiplier（每个撤离点一个倍率）
- bonus_event_pool（撤离专属事件）
- risk_factor（M5 风险系数）

工程师本能 = "加字段加机制"。

### 用户原话纠偏

"不需要在撤离点本身上做文章，收益应该是越深入靠事件本身去驱动的价值，而不是在撤离点的时候做的硬继承"

### 用户设计哲学（远比我推荐的好）

1. 撤离点 = **拓扑层的决策出口**，不是奖励放大器
2. 收益完全由**路上事件本身**驱动（深处事件产物档次更高 = 节点池产物曲线 GDD-04 解决）
3. 撤离时**没有任何硬继承倍率**——撤了多少 = 路上拿了多少
4. ExtractionService 不读资源、不算倍率、不持有任何收益逻辑——纯粹"广播 expedition_ended signal + 触发 SaveService 收尾"

### 这个修正的核心好处

1. **撤离机制纯粹**：单一出口，无奖励计算
2. **数据驱动一致**：所有产出由事件配表决定，不再有撤离点这一层"二次乘法"
3. **降低系统耦合**：撤离点不需要知道资源 / 倍率 / 风险系数 / 加成池
4. **平衡更纯净**：GDD-04 只需平衡"节点池产物档次曲线"（浅 → 深档次递增），不再平衡撤离倍率
5. **"伏击撤离点"语义正确**：玩家选偏僻撤离点的真实动机 = "路上少遇怪 / 体力消耗低"，而非"撤离时奖励倍率高"

## 20:14 GDD-03 §2 事件引擎落地

### §1.3 EventSlotDef 简化（与 §2 对齐）

将 fixed / random_pool / conditional 三种 slot_kind 合并为单一 weighted_pool（含 EventCandidate 列表 + condition + "无"作为合法候选）。leave_location_event / extraction_event 两个特殊类型保留。

理由：用户原话举例"30% 战斗 / 20% 拾宝 / 50% 无"用 candidates 列表+权重就能表达，不需要单独的 conditional/fixed slot 类型。机制更少、表达力反而更强。

### §2 事件引擎核心设计

1. **唯一内容触发口**：所有节点内事件、撤离、leave_location 都通过 EventEngine 解析；BattleResolver / ExtractionService / LocationLeaveService 都是它的下游 handler，不能反过来
2. **事件类型清单 8 种**（M3 实装 4 + 特殊 2）：battle / option / loot / story（实装）+ rest / encounter（schema 占位 M4-M5）+ leave_location_event / extraction_event（特殊）
3. **数据结构**：EventTemplate（模板）+ EventCandidate（槽内候选）+ EventContext（运行态上下文）+ EventResult（结果）
4. **加权候选池机制**：用户定调"无"作为合法候选；过滤 condition_expr → 按 weight 抽 1 → 可能是 event_id 或 ""
5. **事件解析流程**：进节点 → 对每槽抽事件 → 分发到 handler → handler 返回 EventResult → EventEngine 统一应用副作用（service 写出）→ broadcast event_resolved signal
6. **副作用集中应用**：handler 算结果不直接改 state，由 EventEngine 通过 service 写。跟 ADR-0002 战斗"算改分离"同源
7. **事件之间共享信息只 2 通道**：service（推荐）+ EventContext.recent_events（短期，进新节点重置）。严禁 handler 持有彼此引用 / 读其它节点的 NodeInstance 内部
8. **RNG 强制由 ExpeditionState.seed 派生**：派遣弟子可模拟、存档可复现
9. **配表** 事件模板.xlsx 6 sheet：主表 + 4 类型分表（battle/option/loot/story）+ 候选池

### M3 实装范围

- 4 个 handler 类（BattleEventHandler / OptionEventHandler / LootEventHandler / StoryEventHandler）
- ~20-30 条 EventTemplate 配套 qiyun_valley 地图
- 5 类风险预防（隐式耦合 / 权重失衡 / RNG 漂移 / 后果类型膨胀 / 死循环）
- 3 个扩展点（嵌套事件 / 事件链 / DSL 扩展）→ M5

### 元教训 U：机制合并 = 设计简化

§1.3 EventSlotDef 之前 5 种 slot_kind（fixed / random_pool / conditional / leave / extraction）→ §2 简化为 3 种（weighted_pool / leave / extraction），通过让 weighted_pool 的 candidates 持 condition + "" 占位吸收掉前三个。

教训：当 schema 里出现并列的 N 个枚举值且功能高度重叠（fixed = 1 candidate / random = 多 candidate 等权 / conditional = candidate 加 condition），应该合并到带元数据的单一类型。机制少则平衡少、配表简单、代码分支少、新策划学习成本低。

这跟元教训 S 是同条经验的两面——"工程师本能 ≠ 设计哲学"在 schema 设计层的体现。

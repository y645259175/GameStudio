### 元教训 KK：架构哲学比单点设计重要

我之前一直在做"具体设计"——三幕模型 / 五行 / 拟合 / 接入点等。今天用户给了一条**架构级哲学**："契约层 vs 玩法层分离"。这是**比单点设计更上位的边界划分**。

教训：当用户说一句话能影响多章节文档时，**先识别它是架构性（影响多文件）还是设计性（仅影响当前文件）**。架构性的要立刻：
1. 写入"工程纪律"区（GDD-01 §6 这种）
2. 评估对既有章节的影响（哪些违反了哲学）
3. 列出落地步骤（重构 / 拆分 / 新增）

不要急着应用到当前章节就完事——架构纪律一旦定，所有章节都受影响。

### 元教训 LL：渐进迁移 vs 一次性重构

GDD-02 已写完且体量大。一次性删除所有玩法段会带来：
- GDD-04 起草期玩法定义真空
- 大幅 git diff 增加 review 难度
- 万一 GDD-04 设计有问题需要回滚

渐进策略：
1. GDD-02 顶部加 §0 重构说明（路线图）
2. 新建 GDD-04 完整内容
3. GDD-04 PASS 后批量删除 GDD-02 旧玩法（小节内加迁移指针）

教训：**架构重构不是"原子操作"，要分多步骤，每步可独立验收**。这次的 §0.5 进度表就是这种思路的体现——明示哪些已做、哪些待做。

### 元教训 NN：哲学落地的具体动作

GDD-05 §7 培养子系统是 v3.1 哲学最直接的落地：
- GDD-05 → BuffService.apply（建筑挂 buff）
- GDD-04 → 公式自动读 buff（cultivation_multiplier 聚合）

这条范式以后所有"修饰其它系统行为"的子系统都该用——通过 buff 接口注入 modifier，不直接调函数 / 不读字段。

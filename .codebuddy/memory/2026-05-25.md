# 2026-05-25 工作笔记

## xiuxian · ADR 三连重构（重要架构演进）

用户审 ADR-0003 / 0005 时提出三个关键纠偏，每个都是核心架构问题：

### 1. injury_level 不应该是角色字段

用户原话："injury_level 作为角色属性的单独维度有点问题，这种不是应该归属于 buff 系统里面，然后受伤系统通过监控 buff 的变化以影响游戏吗？"

修正：
- 删除 `Character.injury_level` 字段
- 受伤值 = `BuffService.sum_attribute(c, "injury", "general_wound", "level")` 查询结果
- InjuryService 是 buff 的**消费者 + 监控者**，不持有数据
- 订阅 BuffService.buff_applied/removed/attribute_changed signal，到 100% 时触发 ActionState DEAD

精神：受伤是修饰器（buff），不是角色固有维度。让 InjuryService 简化版（M3）→ 复杂版（M5+ 拆细中毒/外伤等）的升级路径完全平滑，**不破坏 Character schema**。

### 2. Buff 注册改为双表（策划友好）

用户原话："把整个 buff 系统的注册变成一个外部表格，策划可以通过改表实现注册新 buff..."

修正：
- **表 A · BuffType 定义表**（`data/buffs/buff_types.tres`）：大类 / 小类 / 数值 schema / 适用 target / tags / stack policy / handler
- **表 B · BuffInstance 模板表**（`data/buffs/buff_instances.tres`）：buff_id + 引用 type + 默认数值 + 时长 + source

各系统调用 `apply_by_id("buff_xxx", target)` 直接挂 buff，**不需要硬编码任何字段**。

广播 / 访问 / 监控全部通过表 A 知道有哪些类型、字段。加新 buff 类型 = 加 1 行表 + 写 1 个可选 handler。

### 3. 宗门也应该是有状态有属性的实体（关键扩展！）

用户原话："除了角色属性，是不是也应该存在宗门的状态和属性？"

之前完全没设计 Sect 数据结构，是个重大遗漏。

修正：
- 新建 ADR-0006 宗门数据结构
- Sect 实现 IBuffable（不只是角色，宗门 / 历练地图 / 区域都可挂 buff）
- BuffService 抽象 target 为 IBuffable，applicable_targets 字段约束 buff 类型适用范围
- Sect 字段：name / faction / reputation / resources / buildings / member_ids / relations / milestones / buffs
- SectService 是 Sect 数据的唯一入口；InventoryService / BuildingService / ReputationService 做领域逻辑，**通过 SectService 读写**

**宗门 buff 用例**：
- `cultivation/qi_acceleration`（SECT）：灵气潮汐挂宗门，消费方 fan-out 到全弟子修炼
- `external/under_attack`（SECT）：邻宗来袭 debuff
- `internal/disciple_unrest`（SECT）：弟子心性低，加叛门概率

### 元教训（非常重要）

#### 教训 A：架构是迭代演进的，不是一次写完的

ADR-0003 v1（单 enum） → v2（区分死亡/传位） → v3（三维度拆分） → v3.1（删 injury_level 字段）。
每一轮都是用户审视后纠正 AI 的架构错误。AI 应该：
- 不怕被否决，每一轮重写都让架构更好
- 写 ADR 时**主动列候选方案**，让用户能精准指出"哪个候选才对"
- 注意"看似简单实际错误"的设计——单 enum / injury 字段都是这种

#### 教训 B：通用化 = 抽象出共性 + 数据驱动

Buff 系统通用化的三层：
1. **共性抽象**（IBuffable 接口）—— 角色 / 宗门 / 地图 / 区域都可挂 buff
2. **数据驱动**（双表注册）—— 类型定义和实例模板分离，策划可改
3. **消费方实现领域逻辑**（fan-out / 监控 / 简化↔复杂升级）—— BuffService 不感知领域

这是 §6.9 解耦原则的最佳实证。下次设计任何"跨切面修饰器"系统都应该走这条路。

#### 教训 C：实体识别比字段细化更重要

之前我只识别了"Character"一个实体，把宗门数据散落到各 service。
用户提示"宗门也应该有状态和属性" → 立刻意识到 Sect 是独立实体。
**架构层面，先识别有哪些实体，再细化每个实体的字段**——这是 ECS 思维 / DDD 思维的标准实践。

#### 教训 D：M3 简化版必须有"未来扩展路径"

InjuryService M3 简化版只看一个 buff（`general_wound`），但通过 `sum_attribute` 接口查询。
未来加中毒 / 外伤等 subtype 时，把查询改为 `sum_attribute_by_category("injury", "level")` 即可。
**Character schema 不变**——这是真正的"框架开放性"。

下次写"M3 简化版"时一定要同时写"未来扩展点"注释，才能避免 M5 重构。

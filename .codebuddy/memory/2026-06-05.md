### 元教训 PP：精简不是删除，是"砍内容 + 留接口"

用户要"精简但保留扩展性"。正确做法不是简单删 5 个建筑，而是：
- 删建筑的"内容"（模板数据 / M3 实装）
- 留建筑的"接口"（扩展空槽 / schema 占位 / 按 kind 分发的工厂）

这样 M4 加回来时是"填空"不是"重写"。这跟 GDD-03 §5 派遣"M3 不实装但不挖坑"、GDD-04 心境"schema 占位"是同款思路。

### 元教训 QQ：合并优于并列（药圃→丹房）

药圃单独成建筑在极简下价值太薄（只月产药材）。并入丹房后丹房成"自给自足炼丹链"，玩家心智更完整，建筑数也降了。

教训：极简时，**价值单薄的建筑/系统优先考虑"合并进相关建筑"而非"独立保留"**。判断标准：这个东西单独存在时玩家会不会觉得"它就干一件小事"。

### 关键设计点

1. **扩展空槽的"看得到建不了"**：M3 玩家能看到 3 个锁定空槽 + 解锁条件提示，形成成长预期，但 M4 才填内容。allowed_building_ids 已预填 M4 建筑 id，unlock 挡住。

### 关键决策

1. **三层架构**：source（人编辑，进 git）→ baked（运行时加载，gitignore）→ runtime（Dictionary）
2. **CSV 三行表头**：r1 = convert 指令（pkey/fkey/json/int/csv/...）/ r2 = 中文表头 / r3 = 英文字段名
3. **CSV 与 .tres 分工**：扁平多行用 CSV、嵌套深单实例用 .tres（不要二选一）
4. **烘焙脚本** `tools/bake_data.py`（M3 实施）：
   - 跳过 # 注释行
   - 按 r1 convert 类型校验
   - 主键唯一性 + 外键完整性 + 类型范围 + JSON 合法性
   - 输出 `data/baked/<table>.tres`（Godot Resource，运行时 O(1) load）
   - 失败退出码非零，CI 拦截
5. **烘焙触发**：开发期 watcher / pre-commit hook / export preset 三处
6. **业界对照**：Unity ScriptableObject、Unreal DataTable、腾讯 SLG LUA 表都是同一思路（源/中间/运行时三层）

### 设计精神

- **运行时不允许直接读 CSV**（性能 + 校验集中度）
- CSV 只支持单值外键，多对多拆中间表（避免复合字段）
- 字段命名：snake_case + bool 动词开头 + 主键 `<entity>_id`
- VSCode 推荐插件：Rainbow CSV + Edit CSV（不推荐 Excel 直接编辑，会改换行符 / bom）

### 失败根因（自我反思）

1. **三行表头制（# r1 convert / # r2 中文 / r3 英文）实测不友好**：
   - VSCode Edit CSV 网格视图把 `#` 行也当数据行，干扰严重
   - JSON 字面量字段（`"{""level"":10}"`）在网格视图里挤成长字符串，策划改不了
2. **没问清楚编辑场景就推方案**：用户想要 Excel 网格点格子改，CSV 三行表头制是给文本编辑设计的
3. **没教用户怎么用插件打开网格视图**：默认 VSCode 看 CSV 就是糊在一起的，没解决"打开方式"

### 修复（schema sidecar 模式）

废弃三行表头制，改为：

- **CSV 文件只放纯数据**（一行真 header + N 行数据）
- **元信息（中文名/类型/校验/默认值/applies_when）搬到同名 `.schema.toml`**
- JSON 嵌套字段拆成扁平列（`attr_level` / `attr_percent` / `attr_consecutive_months` / `attr_element` / `attr_amount`）
- 跨列依赖用 `applies_when` 在 schema 里表达，烘焙脚本校验
- bool 列只接受 0/1（不再接受 true/false/中文）

- `data/source/buff_types.csv` 重写：删 # 注释行 + attributes_schema 用紧凑语法 `name:type:min:max:default`
- `data/source/buff_instances.schema.toml`（新增）：列类型 / 中文名 / fkey / applies_when
- `data/source/buff_types.schema.toml`（新增）
- `.vscode/extensions.json`（新增）：自动推荐 Rainbow CSV + Edit CSV + Even Better TOML + YAML

### 元教训 J：编辑工具决定数据格式，不是反过来

我先选了 CSV 三行表头制（业界 SLG 常见），再来推插件适配。但用户视角是反的：**先确定编辑工具是 Edit CSV 网格视图，再设计数据格式让网格视图友好**。

## 17:35 配表范式定型 v1.0（CSV/sidecar 方案彻底废弃）

### 起因

用户上传了真实工业化项目的 BUFF 配置表样例（`projects/xiuxian/data/table/BUFF系统.xlsx` + `TEXT/文本表_基础文本表.xlsx`），并引入 user 级 excel-engineer skill 作为参考。要求：

1. 数据和表格分开（**导表**机制，运行时不读 xlsx）
2. 稳定范式，未来新表都遵循
3. AOEM 是私有项目，**落地文档不能引用**
4. 烘焙后的运行时格式也要遵守同一范式

### v1.0 范式（已落地）

**4 层架构**：
1. Layer 1 源表：`data/table/<TableName>.xlsx` + `data/table/proto/<name>.schema.toml`（程序员维护）+ `data/table/TEXT/文本表_*.xlsx`
2. Layer 2 烘焙：`tools/excel_convert.py`（增量 hash 比对 + watcher + validate 模式 + 退出码 CI 集成）
3. Layer 3 产物：`data/baked/<name>.tres`（Godot Resource，主格式）+ `data/debug/<name>.json`（外部工具用）+ `_manifest.json`
4. Layer 4 运行时：`game/scripts/data/data_registry.gd` autoload（`get_row` / `get_table` / `get_field` / `text` 4 个 API）

**5 条铁律**：
1. 源表只能 .xlsx，schema 在 .toml
2. 表头两行制：第 1 行中文（含"备注"列）/ 第 2 行英文字段名 / 第 3 行起数据
3. 运行时禁止读 .xlsx / .csv，只能通过 DataRegistry 读 .tres
4. commit 前 `--validate` 必跑
5. schema 与 xlsx 字段不一致 = 编译期错误

### 关键技术点

- **承上规则**：`inherit_when_blank = ["buff_main_id"]` 列空白时沿用上一行（多 subtype 共享 main 的常见写法）
- **dynamic 类型**：`type_resolver = "BuffType[{buff_subtype_id}].buff_param1_type"` 反查类型，支持变长参数（buff_param1-5 不同 buff 类型用法不同）
- **tid 机制**：`type = "tid"` + `fkey = "TextTable.key"`，文本表独立、多语言扩展只需加列
- **glob 配对**：文本表用 `target_xlsx_glob = "TEXT/文本表_*.xlsx"`，多文件合并到一个 .tres
- **增量 hash**：`source_hash = sha256(schema + xlsx)`，未变 skip，2ms 完成

### 实测结果

xiuxian 实跑：
- BUFF系统.xlsx（5 buff 类型 + 5 buff 实例）+ 文本表（3 条文案）
- 全量烘焙 17ms，validate 14ms，增量 skip 3ms
- BuffInstance buffid=5 的 ARRAY 字段 `10,20,30,40,50,60` 正确解析为 `[10,20,30,40,50,60]`
- dynamic 类型反查工作正常

### 元教训 V：层级翻转的危险与价值

v1 → v2 是把"动作"从 handler 层级降到 action 层级——这种翻转会让前一版本所有相关数据结构失效（EventTemplate / EventResult / handler 8 个类全废）。但翻转后表达力显著提升：一个事件能含选项 + 战斗 + 奖励 + 跳转，跟玩家心智一致。

教训：
1. 当用户说"X 不是 Y，X 是 Y 的一部分"时，**警惕这是层级翻转的信号**——立即停下展开新模型，不要在旧模型上 patch
2. 翻转后必须留痕（"v1 → v2 演进"段），让未来读文档的人知道为什么这样设计
3. 翻转的代价是文档大段重写——没办法绕开，硬着头皮写

## 17:23 GDD-03 §4 撤离与超时落地

### 设计要点

- **三种结局对偶**：主动撤离 / 超时强撤 / 团灭收容，都最终走 `extraction` action 但 reason 不同
- **统一收尾哲学**：3 种 reason 的资源处理都是\"路上落袋原样返回\"，区别仅在伤势 buff + 回宗天数
- **action 边界触发**：timeout / defeat 不打断阻塞型 action（show_options / start_battle），都在 action 边界检查 pending 标记
- **优先级**：defeat > timeout > extraction（同时触发只走优先级最高的）
- **数据驱动**：3 种结局的差异化效果（apply_buff 伤势 / 回宗天数）配在系统事件 after_phase 里，service 不硬编码
- **存档粒度**：节点边界 + 撤离结算后；不存档事件中途（玩家中途退游回到节点起点）

### 3 个新增系统事件

- `__sys_extraction__` after: extraction(reason=\"active\")
- `__sys_timeout__` after: apply_buff(severe_fatigue) → extraction(reason=\"timeout\")
- `__sys_defeat__` after: apply_buff(severe_injury) → extraction(reason=\"defeat\")

### 新增组件

- TimeoutWatcher / DefeatWatcher：监听信号标记 pending
- ExtractionService.settle(ctx, reason)：统一结算入口，幂等

### 边界情况清单 7 项（§4.6）

最关键 3 项：
- 撤离节点同时刻时钟归零 → 撤离优先（已走到了算成功）
- 同归于尽（赢战斗但 hp=0）→ defeat 优先于战胜后的 give_loot
- 撤离节点危险事件团灭 → 走 defeat 路径不再触发该节点的 extraction

### 元教训 DD：边界情况要列清单

§4.6 列了 7 个边界情况。这些不是设计师能凭直觉穷尽的，必须**按"事件A + 时点B + 结果C"组合矩阵**扫一遍：
- 时点（节点切换 / 事件中 / 阻塞 action 中 / 战斗中 / 选项中 / 战斗结束瞬间）
- 触发（撤离 / 超时 / 团灭 / 资源耗尽 / 网络异常 / 关游戏）
- 优先级（哪个先发生）

教训：**边界情况清单是 GDD 的硬通货**——后端开发拿到清单就能直接写 unit test；没清单的 GDD 等同于把这工作推给了实现期的 debug。下次写每章都补一个 §X.6 边界情况清单。

## 19:27 §6 战斗框架（修仙五行 DNA 注入）

### 用户原话定调

\"战斗框架需要保留内部可能拓展的战斗规则，但是目前仅仅需要比战斗力的数值大小即可。同时在计算战斗力时保留五行相生和相克的原理\"

附两个例子：
- A=[fire, earth] / B=[metal, water] → A +40% / B +20%
- A=[water, wood, fire] / B=[earth] → A +40% / B +20%

### 关键设计

1. **接口走 ADR-0002**（不复述），M3 实现 = StatSimulator
2. **战力公式三层乘法**：base_power × (1 + sum(buff)) × (1 + element_bonus)
3. **五行相克 5 对**：金克木 / 木克土 / 土克水 / 水克火 / 火克金 → 每命中一组 +20%（笛卡尔积）
4. **五行相生 5 对**：木生火 / 火生土 / 土生金 / 金生水 / 水生木 → 自属性集内每命中一组 +10%
5. **加成是加法不是乘法**：counter + generation 直接累加成 element_bonus
6. **配置化**：counter_bonus_per_match=0.20 / generation_bonus_per_match=0.10 / power_ratio_dominate=1.2 全在配表（数值平衡可独立调）
7. **胜负判定**：power 差 ≥ 1.2x → 碾压；差距小走 RNG 滚

### 留待用户确认 2 个问题

D-1：单属性功法是否启用相生（方案 B 算法版 vs A 严格版）— 用户原例 1 暗示 A，但我倾向 B（直观一致）
D-2：自属性集相生是否去重（A=[wood,wood,fire] 算 1 组还是 2 组）— 我倾向 A 去重

### 元教训 GG：用户给的举例必须严格校验

我用 §6.4.2 算法跑用户原例 1：算出 +50%/+30%，跟用户给的 +40%/+20% 不一致。原因：用户举例时可能只演示\"克制\"加成，没把相生展开。

我没擅自改用户数据，而是在 §6.D-1 把这个不一致暴露出来留给用户拍。这是个好习惯——**用户给的数字与文档算出来不一致时，不要硬调算法去匹配，而是问清楚\"举例的语义是什么\"**。可能：
- 用户举例不严格（只演示一个维度）→ 算法对，举例补全
- 算法过度泛化（算了不该算的）→ 算法收紧

只有用户能定。

### 元教训 HH：默认值数字也要进配表

counter_bonus_per_match=0.20 这种\"明显是规则配置\"的数字，新人会写在代码里。一旦平衡需要调，就要改代码 commit。这是反范式。

教训：**任何\"将来可能为了平衡调整\"的数字，从一开始就放配表**。即使配表初始只有 1 行 1 列也值得。M4/M5 的改动成本和心理负担差 10 倍。

类似还有：power_ratio_dominate / fog_lookahead_layers 默认 4 / 回宗天数 1/3/7。都已落配表。

## 19:06 §5 派遣弟子（拟合范式 + M3 兼容性纪律）

### 用户原话定调

\"派遣系统设计上其实是做一个拟合，不需要真正地走图过事件，而是根据地图配置，映射一个能按照概率分布推算去推算历险结果的系统，M3 不用实现，在这里稍微记录和展开一下，确保后续开发的兼容性即可\"

### 关键设计精神

1. **派遣 != 自动跑图**：本质是\"拟合一个分布函数 f(地图配置, 弟子, 策略) → DispatchResult\"
2. **每个 action_type 都需要分布版实现**（M4）：start_battle 走战力胜率公式 / give_loot 走 LootTable 期望抽样 / show_options 走 strategy 自动选 / random_branch 走 weights 直接抽
3. **M5 替代方案**：让 EventEngine 跑无 UI 的\"无头模式\"。M4 走拟合，性能更好

### M3 兼容性纪律 6 条（review 红线）

§1-§4 已经满足这 6 条，本节固化为派遣兼容性纪律：
1. RNG 必须从 ExpeditionState.seed 派生
2. EventEngine 不依赖 UI 单例
3. action 副作用通过 service 写
4. EventContext 含 actor 字段（区分主角 vs 派遣弟子）
5. BattleResolver 同步骨架
6. Character 数据结构含完整 skills/equipped/status_effects

任何 commit 违反 → 拒收。

### M3 必须做的事（不实装但不能挖坑）

- 4 个类定义文件就位（DispatchTask/DispatchStrategy/DispatchResult/DispatchService）
- DispatchService autoload 注册，body 抛 NotImplementedError
- 配表 schema 预留：历练地图.xlsx 加 DispatchProfile sheet（标注每张图是否允许派遣）
- §5.4 六条 review 红线 enforce

### 元教训 EE：M3 不实装的 schema 占位是关键防线

派遣 M3 不实装，但**M3 的设计不能挡住 M4 实施**。这种\"留接口不留实现\"的纪律比直接\"M4 再说\"更工程化——M4 接手时不需要回头改 §1-§4 的核心代码，只需在预留位置填实现。

教训：**任何\"M4/M5 才做\"的功能，必须列出 M3 期间的兼容性约束**。否则\"先做 M3 再说\"会变成\"M4 来时发现 M3 设计挡了路，要重做\"。这跟 ADR-0003 角色状态机预留 skills/equipped 字段是同款思路。

### 元教训 FF：拟合 vs 模拟的工程取舍

\"派遣\"自然而然让人想到\"自动跑图\"——把玩家亲跑的流程脱壳跑一遍。这是**模拟（simulation）**思路。

用户给了**拟合（fitting）**思路：直接用概率分布推算结果，跳过事件序列。

两者的本质区别：
- 模拟：复用既有引擎 → 行为一致 → 性能慢
- 拟合：写第二套实现 → 性能快 → 与亲跑可能漂移

教训：当面对\"自动版/异步版\"功能时，**先问\"是要忠实复用还是性能优先\"**。修仙派遣的核心玩家心智是\"运营权衡\"不是\"代入决策\"，所以拟合更合适——派遣弟子的结果**应该**比玩家亲跑漂移一点（玩家亲跑应该有微小优势，给玩家\"我比派遣更强\"的成就感）。

### 元教训 SS：批量执行的节奏

12 步 todo 一次性串行做完。每步 commit/lint 不间断。这种"批量执行"模式适合：
- 模板化任务（每个 GDD 都是 7-13 节固定结构）
- 引用已存在的设计决议（前几章 GDD 已定，本次只是固化骨架）
- 用户授权"一次到位"（非"分步确认"）

避免反模式（记忆 99700509 §10）："分阶段确认"在已有清晰路径时是延迟交付的借口。

### 元教训 TT：延后细节存档的模式

`docs/m1-deferred-details.md` 是个新模式：
- 主章节保持简洁（M3 必需 only）
- 延后内容写存档（M4-M7 才展开）
- 展开纪律：搬回主章节后删存档对应条目

这避免了两种反模式：
- A：主章节塞满未来内容 → 阅读负担 + M3 阶段无关紧要
- B：完全不写 → M4 启动时遗忘当初思路

折中：写思路骨架 + 集中存档，展开时按需展开。

### 元教训 UU：渐进迁移 vs 一次性删除

GDD-02 玩法段没有立刻删除（虽然内容已迁到 GDD-04/05/06）。采取"加迁移指针 + 待用户审 PASS 后批量删"。理由：
- 用户可能审 GDD-04 时发现某条玩法迁错位置 → 需要回头改
- 立刻删 → 万一需要回滚成本高
- 加指针 → 文档可读 + 迁移轨迹清晰 + 回滚便宜

教训：架构重构是"加指针 → 验证 → 删除"三步，不要一步删干净。

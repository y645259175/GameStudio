#### 教训 A：和 Identity 一样的"先简后丰"原则要全局贯彻

之前 ActionState 列了 5 个状态（IN_CLOSED_DOOR / RECOVERING / DEFECTED 都是"先想周到"的产物），但用户提示"和身份一样"——Identity 我列了 4 个就够，ActionState 也应该 M3 只放 3 个。

#### 教训 B：YAGNI 原则在架构层面同样适用

我之前在 ADR-0006 里写了 7 处"M4 多宗扩展"相关内容（风险 / 候选对比 / 影响 / 字段表 / 注释），但用户一句"先做好自己宗门"就让这些全部失效。

我犯的错误是**把"未来可能"当成"现在必做"**——我以为"为多宗预留接口"是好的工程实践，但实际上：
- 玩家宗门数据归口（SectService）是为了 §6.9 解耦，**和多宗无关**
- 把"为多宗预留"作为论证理由，反而让设计意图模糊
- 真到需要多宗时，加 `get_sect_by_id` 接口是 5 分钟工作量，不需要现在就承诺

下次写 ADR 时：**论证理由只用当前真实需求**，不要用"未来可能扩展"撑论据。

这是设计纪律，不是技术选择。

## 21:50 GDD-02 §2 境界系统定稿

### 用户核心设计（含原创公式）

**结构**：5 大境 × 9 小境 = 45 层 + 飞升

**修炼机制**：
- 小境界 1-8 → 满即升
- 9 层 → 进入瓶颈（不自动升）
- 瓶颈期累积"修炼分"，越久概率越高

**突破概率公式（用户原创）**：
```
最终概率 = clamp(基础概率 + 增益叠加, 0, 1)
基础概率 = (基础分 + MAX(修炼分, 10) + 灵根分 + 悟性分) / 难度分
  修炼分 = 瓶颈后月数 × 单月基础修炼分(全局) × 悟性/100
  灵根分 = Σ rootᵢ (i ∈ 功法绑定灵根)      ← 用户选 B 简单和
  悟性分 = (悟性 - 100) / 10
```

设计精妙点：
- **悟性双重作用**：直接 + 间接（× 修炼分），成为核心稀缺属性
- **MAX 保底 10**：瓶颈瞬间就能冲，不锁死玩家
- **修炼分清零规则**：突破失败重置（防"前期失败白嫖"）
- **增益叠加层**：基础公式是骨架，丹药 / 道具 / 事件留扩展位

**失败惩罚**：跌 1 小境 + 修炼分清零（用户选 C 反向进度）

**上限处理**：clamp [0, 1]，可达 100%（用户选 A 无 95% 上限）

### 寿元规则（A 实数月 + C 不外显 + 个体差异）

- 凡人 50-70 年随机（可配）
- 每境 +80-100 年（每境单独配）
- buff 系统支持永久 / 临时寿元修饰（血脉 / 延寿丹 / 禁术 / 诅咒）
- **平时不显示**寿元数字
- < 50 月触发"寿元将近"状态栏提示
- = 0 直接 DEAD（无坐化事件，玩家必须在警告期处理）

### 游戏结束条件（用户定调）

> "如果门派没有一个人则游戏结束"

```
all sect.members.action_state == DEAD → GameOver
```

### 元教训

- **公式可配置化是策划友好的关键**：所有"基础分 / 难度分 / 全局修炼分 / 寿元上下限"都配在数据表，策划不需要碰代码就能平衡
- **悟性这种"双效属性"是良好设计**：让一个属性的提升带来双倍价值，鼓励玩家培养稀缺资源
- **基础公式 + 增益层**：公式留好骨架，buff / 道具增益叠加在外，避免后续修改公式破坏存档
- **"不外显数字"是反内卷设计**：寿元、未来可能也包括"突破概率精确值"、"修炼分精确值"——让玩家"感受"而非"算计"

# gdd-skeleton · GDD 建议骨架（不是强制模板）

> **重要**：本骨架是**起点建议**，不是必须遵循的固定结构。
>
> 真实项目的章节由 `design-review` skill 的"概念对话"步骤决定。这里给出的是常规情况下大多数项目会用到的章节，可作为讨论的对照参考。
>
> **如果你的项目讨论后发现章节差异较大，那是正常的，不需要硬套本骨架**。

---

## 最小覆盖（5 项，所有项目必须有）

无论项目如何，GDD 至少必须覆盖：

| 维度 | 标题示例（可调） | 最低产出 |
|---|---|---|
| 1 概述 | `## 概述` | 一句话定位 + 目标玩家 + 类型 + 范围声明 |
| 2 核心玩法 | `## 玩法循环` / `## 核心机制` | 玩家在玩什么（秒级 / 局级 / meta 至少 1 层） |
| 3 系统设计 | `## 系统设计` | 关键系统的职责 / 规则 / 边界 |
| 4 视觉与美术 | `## 视觉与美术` | 风格关键词 + 色板（最少）+ 参考图引用 |
| 5 交付与验收 | `## 交付与验收` | DoD + 风险 + 已知限制 |

> 这 5 个维度不可省，少于 5 个 → review BLOCKED。

## 建议骨架（约 8 节，仅供参考）

> 大多数中等复杂度项目可能会用到下面这 8 节。**先看你项目的概念对话产出**，再判断这 8 节里哪些用得上、哪些不需要、是否需要新增。

```markdown
---
gdd_id: ${GDD_ID}
status: draft
last_review: ${DATE}
sections: []                    # 由概念对话填入实际章节标题
skeleton_deviation: none        # none / minor / major
deviation_rationale: ""
---

# ${GDD_TITLE}

## 概述
<!-- 一句话核心概念 + 目标玩家 + 类型定位 + 范围声明 -->

## 玩法循环
<!-- core loop / meta loop（如果有 meta） -->

## 视觉与美术
<!-- 风格关键词 / 色板 / 参考图 -->

## 系统设计
<!-- 关键子系统拆解 -->

## 数值与平衡
<!-- 数值表锚点 + 关键公式 + 平衡假设 -->

## 内容与节奏
<!-- 关卡 / 章节 / 故事 / 进度曲线 -->

## UX 与 HUD
<!-- 界面流转 + HUD 元素 + 无障碍占位 -->

## 交付与验收
<!-- DoD + 风险 + 已知限制 -->
```

## 何时该砍 / 该加章节

> 这是**判断指南**，不是硬规则。

### 砍章节的常见情况

| 砍掉 | 适用项目 | 原因 |
|---|---|---|
| `## 内容与节奏` | 单屏休闲 / 街机风（如 breakout / 俄罗斯方块）| 没有"章节"概念，节奏由数值曲线表达 |
| `## UX 与 HUD` | HUD 极简且不变化的项目 | 可并入"视觉与美术"一小节 |
| `## 数值与平衡` | 数值是固定常量、不需要平衡的项目 | 可在"系统设计"内列字段表 |

### 加章节的常见情况

| 加什么 | 适用项目 | 原因 |
|---|---|---|
| `## 程序生成参数` | Roguelike / 程序化关卡 | 这是核心玩法的支柱，必须独立 |
| `## meta 系统` | 含解锁 / 升级 / 永久进度 | 跨局影响，独立讨论 |
| `## 匹配与同步` | 多人 PvP | 网络模型与单机不同维度 |
| `## 分支结构` | 叙事 / AVG | 文本量大、分支复杂 |
| `## 工具系统` | 沙盒建造 | 玩家"创造"是核心循环 |
| `## 反作弊` | 多人 / 排行榜 | 安全与公平性 |
| `## 数据埋点` | 服务化产品 | 运营驱动决策 |

> 这只是**参考片段**，不是要套的章节模板。每个项目自己的章节必须从概念对话中产生。

## 偏差度判断

| 偏差度 | 定义 | frontmatter |
|---|---|---|
| `none` | 完全用建议骨架的 8 节 | 无需写 rationale |
| `minor` | 砍 / 加 / 改 1-2 节 | rationale 写一句即可 |
| `major` | 砍 / 加 ≥ 3 节，或结构重构 | rationale 必须详写：为什么砍 / 为什么加，必要时另起 `gdd-skeleton-rationale.md` |

---

## 与 design-authoring rule 的关系

- 本模板是 **建议骨架**（参考）
- `rules/design-authoring/RULE.mdc` 是 **强制规则**（最小覆盖 5 维度 + 内容精度三原则 + 锚点稳定性）

冲突时以 rule 为准。本模板的目的是**降低概念对话的起步成本**，不是替代对话。

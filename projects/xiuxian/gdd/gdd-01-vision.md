# GDD-01 · 核心愿景与玩法循环

> 本章是项目"北极星"——后续所有 GDD 章节、ADR、stories 都必须能追溯回这里。
> 后续章节会拆分到 gdd-02 ~ gdd-08（系统 / 数值 / 内容 / UX / 美术 / 音频 / 交付）。

---

## 1. 概述

### 一句话核心概念

**你是一宗之主**：在宗门内修炼、培养弟子、炼丹炼器、经营道场，亲自或派遣弟子外出秘境历练，带回资源以提升宗门实力，最终冲击飞升。

### 目标玩家

- 喜欢经营管理 + 探索决策的玩家
- 修仙 / 武侠 / 东方奇幻题材爱好者
- 偏好节奏可控、单局可暂停的单机沙盒
- 平台：Steam（PC，Windows 优先）

### 类型定位

> 单机 2D 沙盒经营 + 选项式 extraction

混合参考：
- **潜水员戴夫** —— 双层循环节奏（白天/夜晚 ⇄ 宗门/历练）
- **鬼谷八荒** —— 修仙世界观 + 水墨美术 + 角色养成
- **Tarkov / Dark and Darker（lite）** —— 搜打撤退的"带不带得回"张力

### 设计支柱（不可妥协）

1. **两个 50% 必须势均力敌**：宗门和历练任一方变成附属即背离设计意图
2. **"框架开放性"**：所有系统数据驱动 / 接口抽象，VS1 实现简化版但不锁死扩展
3. **决策永远有真实代价**：选项消耗时间 / 资源 / 角色状态，不存在"白嫖"分支

## 2. 玩法循环

### 2.1 Core Loop（每分钟玩家在做什么）

```
┌────────────────────────────────────────────────────────────┐
│                  宗门内务月（10-20 min）                     │
│                                                            │
│   闭关 ─→ 突破检定        炼丹 ─→ 资源 → 战力                │
│      │                      │                              │
│      ↓                      ↓                              │
│   感悟功法              建设建筑                             │
│      │                      │                              │
│      └──────┬───────────────┘                              │
│             ↓                                              │
│      （边际递减触发）→ "该出门了"                            │
└─────────────┬──────────────────────────────────────────────┘
              ↓
┌────────────────────────────────────────────────────────────┐
│              选择历练图（消耗 1-N 个月）                      │
│   新手图 / 灵药谷 / 妖兽巢穴 / 上古遗迹 / ...                 │
└─────────────┬──────────────────────────────────────────────┘
              ↓
┌────────────────────────────────────────────────────────────┐
│         外出历练月（10-40 min · 内部时间百分比制）            │
│                                                            │
│   [入口] ──[节点A]──[节点B]                                 │
│              │       │                                     │
│           [节点C]──[深处]                                   │
│                                                            │
│   每节点：多个事件 / 选项 / 战斗 / 移动                       │
│   时间到 100% → 强制返回 / 撤退失败                          │
└─────────────┬──────────────────────────────────────────────┘
              ↓
        ┌─────────────────────────┐
        │ 资源 / 道具 / 功法残页    │
        │ 回宗 → 加工 → 提升       │
        └─────────────────────────┘
                    │
                    └─→ 解锁更深秘境（循环）
```

### 2.2 Meta Loop（多个循环之上的目标）

```
新弟子招收  →  境界突破  →  解锁高级地图  →  门派声望提升
     ↑                                            │
     └────────── 大世界事件（仙宗大比/邪修入侵）──┘
                            ↓
                       飞升 / 重大结局
```

### 2.3 时间结构（双层时钟）

> ADR：[`adr/0001-double-clock.md`](../adr/0001-double-clock.md)（proposed）

**外层时钟：宗门月历**
- 1 月 = 1 回合，**连续推进**——历练期间也按百分比映射广播月份变化
- 玩家在月初做决策（本月做什么、是否出门、出门去哪）
- 月末结算（建设产出 / 弟子修炼成果 / 大世界事件触发）

**内层时钟：历练进度条**
- 进入历练后切换到百分比制（0% → 100%）
- 每个事件 / 选项 / 战斗 / 移动消耗不同百分比
- 100% 强制返回；提前撤退随时可选
- 道具 / 功法 / 神行术可缩短消耗

**关键纪律**（用户定调 v2）：
- **大世界月份连续推进**：2 月图在 50% 时广播下个月开始；3 月图在 33% / 67% 各广播一次
- **撤退时月数 = `ceil(progress * max_months)`**（向上取整，避免 1% 撤退占便宜）
- **历练中宗门系统也推进**：弟子寿元 -1 / 加工产出 / 建设进度 / 大世界事件等都按月运转
- **存档约束**：只能在大世界（非历练中）存读档；亲自历练出发前自动存档（派遣弟子不触发）

**节奏曲线设计**

| 阶段 | 内务 | 历练 | 历练月数 | 单循环 | 玩家心智 |
|---|---|---|---|---|---|
| 前期（开局-第 1 突破） | 10 min | 10 min | 1 月 | 20 min | 学习系统 |
| 中期（突破后-练气期满）| 15 min | 20 min | 1-2 月 | 35 min | 打磨与扩张 |
| 后期（筑基/金丹+）| 20 min | 40 min | 2-3 月 | 60 min | 长线规划 |

### 2.4 经营压力来源（"为什么必须出门"）

> 用户共识：宗门是主世界，但**单纯闭关会陷入边际递减**，自然推动玩家外出。

#### 内生压力（边际递减原则）

> **设计原则**（用户定调）：边际递减是**通用纪律**，**不是统一公式**——
> 每个系统按自身特性定曲线，但都必须遵守"持续投入收益快速衰减"的精神。
> 详细公式落 GDD-04 经济与数值。

| 系统 | 曲线类型示例 | 调节方式 |
|---|---|---|
| **闭关修炼**（门主自身）| 指数衰减 `(1/2)^t`（月 1=100% / 月 2=50% / 月 3=25%）| `t` = 连续闭关月数；外出后重置 |
| **加工产能** | 硬上限（库存耗尽即停）| 资源补给驱动 |
| **弟子培养** | 阶梯型（功法/法宝瓶颈）| 解锁新内容驱动 |
| **建设产出** | 线性 → 饱和（建筑等级上限）| 升级树驱动 |
| **境界突破** | 阈值型（非线性，需关键资源）| 历练资源 + 顿悟事件 |

**通用纪律**：
- 任何"持续做同一件事 → 累积收益"的系统都必须在 GDD 各章中**显式标出递减曲线类型**（指数 / 阶梯 / 硬上限 / 阈值）
- VS1 的具体数字是占位，GDD-04 会基于平衡假设标定
- 公式参数化（不写死），落到 `data/balance/`

#### 外生压力（主线 / 大世界事件）

- 阶段性实力检测（与主线绑定，例：每若干年仙宗大比 / 邪修扣关 / 灵气潮汐）
- 没达标 → 损失声望 / 弟子叛门 / 资源被抢
- **`WorldEventTrigger` 接口 M2 即建**；钩子目录 M1 列入 GDD-09；实际事件内容 M5 才填
- M3 范围决策见 §7.2（待用户回应）

### 2.5 失败 / 死亡处理

> 用户定调（2026-05-23 v2）：
> - **门主继位有两条路径**：被动死亡（紧急继位，老门主死了不进长老阁） vs 主动传位（老门主入长老阁荣养）
> - **新手图死亡保护 = 事件层面不存在死亡分支**——所有事件 outcomes 只覆盖"无事 / 受伤"

| 场景 | 后果 |
|---|---|
| 历练超时 | 资源部分丢失，强制返回 |
| 主动撤退 | 携带物全部带回（推荐玩家学习的"健康行为"）|
| 角色受伤 | 回宗静养 N 月，期间不可行动 |
| 角色死亡（非门主）| 损失角色 + 资源 + 声望 |
| **门主路径 a · 被动死亡** | 历练战死 / 刺杀 / 走火入魔 / 寿元耗尽 → 强制弹"紧急继位"UI → 必须指定一名弟子继任 → 老门主**死亡**（不进长老阁）|
| **门主路径 b · 主动传位** | 玩家在宗门界面主动选"传位" → 选择继任弟子 → 老门主**入长老阁**（保留全部属性 / 装备 / 技能，可特殊事件出手）|
| **新手图保护**（用户定调）| **事件层面无死亡分支**——所有战败概率分布只覆盖"无事 / 受伤"，永远不到"死亡"。包装：事件烈度 / 危险程度都偏低 |
| 出门门槛 | 新手图允许只带门主单人；非新手图至少 1 弟子陪同 |

> 设计含义：长老阁是**主动卸任的奖励状态**，不是任何前门主的归宿。
> 这给玩家"何时让位"的策略选择空间——继续打 vs 主动让位换长老阁特殊事件触发权。
>
> 实现要点：
> - 事件 schema 中的 `outcomes` 字段，新手图事件不允许包含 `state: Dead` 的分支
> - `CharacterService.transition(...)` 接收 `reason` 参数，区分 `master_died` / `master_abdicated`
> - 详见 ADR-0003 角色状态机

## 3. 视觉与美术

### 3.1 风格关键词

- **水墨写意** —— 鬼谷八荒为核心参考
- **分图层 2D** —— 远山留白 / 中景半写意 / 近景较实
- **宣纸纹理 UI + 毛笔字体** —— 低成本高效果

### 3.2 实现策略

| 层 | 内容 | 实现 |
|---|---|---|
| 立绘 | 主角 / 弟子 / NPC | AI 生成 + 修绘（`art-asset-pipeline`）|
| 场景 | 历练地图 / 宗门建筑 | 图层化 2D，水墨远景 + parallax |

| UI | 宣纸纹理 + 毛笔字体 | shader + 字体导入 |

### 4.2 系统间关系图（高层）

```
TimeService（月节拍 + 历练百分比）
    ↓ 月节拍
ProductionService（建设/炼丹/培养产出）
    ↓ 月节拍
WorldEventService（大世界 / 主线检测）
    
TimeService → ExpeditionService（历练）
              ↓
              EventEngine（节点内事件流）→ BattleResolver（战斗）

              ↓
              ResourceFlow（撤退后资源回宗）
              
所有系统订阅 SaveService（统一序列化 + 版本号）
```

## 6. 技术架构原则（特别章节 · 用户强调）

> 用户原话："项目整体的开发必须必须一定要对后续内容的开放留出足够的框架。"
>
> 进一步明确（2026-05-23 二次定调）：
> "M1 尽量想好大部分系统和内容框架，提前安排好可扩展性，至少要提前知道可能出现的问题点；
> 程序方面要减少系统耦合以防出现各种关联 bug。"
>
> **本章是项目最高优先级的工程纪律**，目标不是"封闭 M1 之外的系统加入"，
> 而是 ① 尽量穷尽规划 ② 提前列出风险点 ③ 解耦设计让后续加系统不引发关联 bug。

### 6.1 数据驱动

- 角色 / 物品 / 事件 / 地图 / 敌人 / 功法 / 技能 / 装备 全部以 JSON 或 Godot Resource 描述
- 代码只读取数据并执行通用逻辑
- 内容设计师可以**不改代码**新增内容

### 6.2 接口抽象（M2 必落地的 4 个）

| 接口 | VS1 实现 | 未来扩展（已知方向）|
|---|---|---|
| `BattleResolver` | `StatSimulator`（双方属性算结果）| **回合制战斗**（详见 §6.8）/ 衍生技能 / 装备 |
| `EventResolver` | 数据驱动选项树解释器 | 可加复杂状态机 / 多角色对话 / 因果图 |
| `ProductionRule` | 简单产出公式 | 复杂排队 / 多工序 / 关键事件小玩法 |
| `WorldEventTrigger` | 月节拍 / 资源阈值简单触发 | 主线条件复合触发 / 派系联动 / 因果链 |

**接口纪律**：所有接口在 M2 即落地（哪怕实现是占位），M3 起接入第一个实现，未来扩展只新增实现类，不改接口签名。

### 6.3 角色统一数据结构（三维度状态 · 用户定调 v3.1）

> ADR：[`adr/0003-character-state-machine.md`](../adr/0003-character-state-machine.md)（v3 三维度）+ [`adr/0005-buff-system.md`](../adr/0005-buff-system.md)（buff 系统）

角色 = 统一 Character 数据结构（实现 IBuffable）+ **三个独立维度**：

| 维度 | 性质 | 值 |
|---|---|---|
| **Identity** 身份 | 长期稳定 | MASTER_CURRENT / DISCIPLE / ELDER / NON_SECT |
| **ActionState** 行动状态 | 即时，每月可刷新 | M3：IDLE / IN_CULTIVATION / DEAD（按系统扩展，参考 Identity 同纪律）|
| **Buffs** 修饰器（含伤病等）| 多个并存 | 由 BuffService 统一管理（详见 §6.10）|

> 三维度正交：门主可以闭关也可以中毒；弟子可以受伤也可以灵气加速。
>
> **关键纪律（v3.1 修正）**：受伤值不再是 Character 字段，是 buff 累计的查询结果。
> 受伤系统（InjuryService）作为 buff 消费者 + 监控者，不持有数据。详见 §6.10。

**身份转移**走 `CharacterService.change_identity()`；行动状态转移走 `set_action_state()`；buff 操作走 `BuffService`。
所有"X 角色能不能做 Y"的判断走 `can_do(character, action)` 综合查询三维度。

### 6.4 时间总线

```
TimeService（singleton autoload）
  ├─ signal month_advanced(月数)
  ├─ signal expedition_progress(percent)
  └─ signal world_event_triggered(event_id)
```
所有系统**订阅信号**，不直接读时钟。

### 6.5 存档（基础原则）

- 第一天就建可序列化结构（统一 `to_dict()` / `from_dict()`）
- 必带 `save_version` 字段（后续迁移用）
- 存档内容覆盖：所有角色 / 资源 / 时间 / 历练当前进度 / 已完成事件
- 详细前瞻设计见 §6.7

### 6.6 主线钩子预留

- 主线事件框架在 M2 即建，但**内容到 M5 才填**（用户里程碑纪律）
- 钩子点：月节拍 / 突破 / 进入特定地图 / 击杀特定敌人 / 资源累积阈值
- 漫画/CG 系统接口在 M2/M3 留好，实际剧情到 M5

### 6.7 存档前瞻设计（**用户特别强调** · M2 必做）

> 用户原话："M2 在实现的时候必须要参考整体未来规划，注意要考虑到未来不断新添加内容的时候也需要考虑存档的问题，因此对于数据结构储存位置等等需要细细考量。"

存档不能"做着做着补上"，必须 M2 一次性敲定下面 5 件事：

| 决策点 | M2 必须确定 | 反例（坑） |
|---|---|---|
| **Schema 版本** | `save_version` int + `migration` 函数链 | 不版本号，加字段后老存档崩 |
| **数据分区** | 角色 / 资源 / 时间 / 历练 / 主线 / 设置 / 战斗 / 装备 / 技能 分独立段 | 全部一坨 dict，加字段全表迁移 |
| **新增字段策略** | 用 `dict.get(key, default)` 兼容旧档 | 强读字段，加新内容 = 老档报错 |
| **未知字段保留** | 加载时不丢弃未识别字段（向前兼容） | 老版本读新档损失字段 |
| **数据存放位置** | 分清"模板数据 (data/，只读)" vs "运行时实例 (savefile，可写)" | 把模板数据存进存档，文件膨胀 |

**M2 强制产出**：
- `adr/0004-save-architecture.md`（存档架构决策 + 兼容策略）
- `data/` 目录组织规范（按系统分子目录）
- `SaveService` 单元测试覆盖：跨版本加载 / 字段缺失 / 未知字段保留

详见 GDD-08 交付与验收 / 工程章节，及未来 ADR-0004。

### 6.8 战斗系统框架（**用户强调 · M1 必须想清楚**）

> 用户原话："要保留一个战斗系统的框架，一开始先用数值对拼填充，
> 后续要补充详细的回合制战斗玩法和过程的，可能衍生出一整套技能、装备的系统。"

战斗系统的**框架** M1 完整定义；**实现**分阶段：

#### 6.8.1 抽象层级

```
┌─────────────────────────────────────────────┐
│  调用方（历练事件 / 主动挑战 / 防守反击）         │
│  → BattleContext{ attacker, defender, env }  │
└──────────────────┬──────────────────────────┘
                   ↓
┌─────────────────────────────────────────────┐
│  BattleResolver（接口）                       │
│   .resolve(ctx) → BattleResult{              │
│       winner, hp_changes, status_effects,    │
│       loot, log_entries, narrative_seed }    │
└──────────────────┬──────────────────────────┘
                   ↓
┌─────────────────────────────────────────────┐
│  实现选择（按 M 阶段切换）                     │
│   M3 (VS1): StatSimulator（双方数值对拼）     │
│   M5+    : TurnBasedEngine（回合制完整流程）  │
│   预留    : ScriptedBattle（剧情演出战斗）    │
└─────────────────────────────────────────────┘
```

**关键**：调用方只看到 `BattleResolver` 接口，**不感知实现**。M5 替换实现时，宗门系统 / 历练事件不需要改一行代码。

#### 6.8.2 衍生子系统（M1 必须列入框架，M5+ 实现）

| 子系统 | M1 框架要求 | M5+ 实现重点 |
|---|---|---|
| **技能系统** | Character 数据结构带 `skills: Array<SkillId>`；`Skill` 数据 schema（id / 类型 / 消耗 / 效果脚本）| 技能编辑器 / 升级树 / 灵根加成 |
| **装备系统** | Character 数据结构带 `equipped: Dict[Slot, ItemId]`；存档分区独立 | 法宝 / 灵剑 / 防具 / 强化 / 镶嵌 |
| **状态效果** | `StatusEffect` 数据 schema（增益/减益/中毒/眩晕等通用框架）| 视觉表现 / 叠加规则 / 解除条件 |
| **战斗日志** | `BattleLog` 结构化数据（每一击 / 命中率 / 暴击）| 战报回放 / 文字播报演出 |

**注意**：上面这些"M1 框架要求"必须落到 GDD-02（角色 schema）+ GDD-03（战斗章节）+ GDD-04（数值），**M3 数据结构里就要有这些字段**（即使 M3 只用到 hp/atk/def）。

> 否则后果：M5 加技能系统时，存档里没 skills 字段 → 老存档加载崩 / 全档迁移痛。
> 这正是 §6.7 §6.9 想避免的事。

#### 6.8.3 战斗接入点（系统耦合最敏感的边界）

战斗会被以下场景调用，每个场景都通过 BattleResolver 接口（解耦）：

- 历练节点内的"挑战"事件（M3 起）
- 宗门被攻击（M4 起）
- 派遣弟子遭遇（M4 起）
- 主线 boss 战（M5 起）
- 仙宗大比 / 比武（M5 起）

**M1 必须把这 5 个接入点列在 GDD-03 / 09**，M2 接口测试覆盖至少其中 1-2 个调用路径。

#### 6.8.4 风险预知

| 风险 | 提前安排 |
|---|---|
| M5 回合制实现时数据结构发现少字段 | M1 GDD-02 把战斗相关字段列全（哪怕 M3 不用）|
| 技能系统加入后破坏现有数值平衡 | GDD-04 平衡公式从一开始就考虑 "skill 未来会注入修正" 的占位 |
| 装备系统加入后老存档没装备槽 | 存档分区独立 + dict.get(key, default) |
| 战斗演出从无到有时美术返工 | M1 GDD-06 标记"战斗演出资产 M5+ 才生产，M3 仅 UI 占位" |

### 6.9 系统解耦原则（**用户强调 · 减少关联 bug**）

> 用户原话："程序方面要减少系统耦合以防出现各种关联 bug。"

游戏开发最常见的 bug 来源 = 系统间的隐式耦合（A 改了 B 没跟上，C 直接读 A 的内部）。
为防止这类"关联 bug"，本项目强制以下解耦纪律：

#### 6.9.1 通信只走 3 种通道

```
┌─────────────────────────────────────────────┐
│  ✅ 允许的系统间通信                          │
├─────────────────────────────────────────────┤
│  1. EventBus signal（异步广播）                │
│  2. Service 接口调用（同步、单向、签名稳定）   │
│  3. 数据共享（只读 data/，写走 SaveService）   │
│                                             │
│  ❌ 禁止                                     │
│  - 系统 A 直接读 系统 B 的内部字段             │
│  - 系统 A 持有 系统 B 的具体实现引用            │
│  - 跨系统的全局静态可变状态                    │
└─────────────────────────────────────────────┘
```

#### 6.9.2 系统间依赖矩阵（M1 必须画出）

GDD-10 系统扩展性总账中**强制**包含一张依赖矩阵：

|  | TimeService | CharacterService | SectService | BuffService | InventoryService | BattleResolver | SaveService |
|---|---|---|---|---|---|---|---|
| 历练系统 | 订阅 month / progress | 读 Character 接口 | 读 Sect 接口 | 读/写 buff（事件给 buff）| 写资源（通过 SectService）| 调用 resolve | 通过它存档 |
| 宗门经营 | 订阅 month | 读/写 Character | **是 Sect 数据的归口** | 应用闭关 / 灵气 buff | 读/写 资源 | — | 通过它存档 |
| 战斗系统 | — | 读 Character 接口 | — | 读/写 buff（战斗状态效果）| 写战利品（通过 SectService）| **是接口本身** | 通过它存档 |
| Buff 系统 | 订阅 month_advanced（tick）| 读 Character.buffs | 读 Sect.buffs | **是接口本身** | — | — | 通过它存档 |
| InjuryService | — | 写 ActionState DEAD | — | 订阅 buff signal + 查询累计 | — | — | 不持有数据 |
| InventoryService | — | — | 通过 SectService 读写 sect.resources | — | **是领域规则**，不持有数据 | — | 通过 SectService 存档 |

**用途**：加新系统时一眼看出该系统会**触碰哪些现有系统**，提前评估"加上去后哪些可能踩雷"。

#### 6.9.3 跨系统改动的"红绳警示"

> 这条是**预防关联 bug 的执行机制**

任何 PR 同时修改 ≥3 个不同系统的核心文件 → 必须在 commit message 加 `[cross-system]` tag，
触发 reviewer agent 强制检查：

- 是否破坏了系统间接口
- 是否新增隐式耦合
- 是否更新了 §6.9.2 依赖矩阵
- 是否需要补 ADR

（具体执行落到 `.codebuddy/hooks/pre-commit-discipline.py`，M2 后期更新）

#### 6.9.4 "M1 之后加新系统"的真正纪律（修正前文）

> 修正：§7.1 / §7.3 措辞从"不允许加"改为"**允许，但必须走预案**"。

新加系统流程：

1. **写 ADR**：决策动机 / 影响的现有系统（参照 §6.9.2 依赖矩阵）/ 兼容性策略
2. **更新 GDD-10**：扩展性总账加这条
3. **存档兼容**：用 §6.7 5 点验证（新字段是否独立分区？是否 default 兼容？）
4. **依赖矩阵更新**：加新行新列
5. **接口检查**：是否打破现有 4 接口（§6.2）的契约

**精神**：M1 不是封闭门，是**先验关卡**——尽量在 M1 想全，但允许后续加，加的时候必须过 5 步预案。

### 6.10 通用 Buff 系统（用户定调 v3 双表 + IBuffable）

> ADR：[`adr/0005-buff-system.md`](../adr/0005-buff-system.md)（proposed v2）

跨切面的"修饰器"通过统一的 BuffService 处理——伤病 / 修炼 / 战斗 / 心境 / 因果 / 灵气环境 / 派系关系等都走 buff，而不是各系统自己加字段。

#### IBuffable 接口（任意实体可挂 buff）

不只是角色——**宗门、历练地图、未来的区域**等都可挂 buff。

```
IBuffable.target_type ∈ { CHARACTER, SECT, MAP, REGION, ... }
```

实现 IBuffable 的实体：
- `Character`（ADR-0003）
- `Sect`（ADR-0006，详见 §6.11）
- `ExpeditionMapInstance`（GDD-03 起草时建）

#### 双表注册（用户定调 · 策划友好）

| 表 | 内容 | 谁填 | 例子 |
|---|---|---|---|
| **表 A · BuffType 定义表**<br>`data/buffs/buff_types.tres` | 大类 / 小类 / 数值 schema / 适用 target / tags / 默认 stack policy | 策划 | `injury/poison`：数值 `[level: 0~100]`，适用 CHARACTER |
| **表 B · BuffInstance 模板表**<br>`data/buffs/buff_instances.tres` | 具体 buff 实例（buff_id + 引用 type + 默认值 + 时长 + source）| 策划 | `buff_poison_event_jungle_001`：type=`poison`，level=30，duration=3 月 |

各系统只需调用 `BuffService.apply_by_id("buff_xxx", target)`，**不需要硬编码任何 buff 字段**。
广播 / 访问 / 监控也通过表 A 知道有哪些大类小类、字段。
加新 buff 类型 = 加 1 行表 + 写 1 个可选 handler，**不改 BuffService 代码**。

#### 核心 API（统一接口处理 IBuffable）

```
apply_by_id(target, buff_id, override?)        # 走表 B 实例化挂载
get_by_subtype(target, category, subtype)
sum_attribute(target, category, subtype, attr_key)
sum_attribute_by_category(target, category, attr_key)   # 跨小类累加（伤病系统升级用）
clear_by_tag(target, tag)
tick_monthly(target)                            # 订阅 TimeService.month_advanced
```

#### 受伤系统（InjuryService）= buff 消费者 + 监控者

> **关键架构修正（v3.1）**：受伤值不再是 Character 字段。

- **不持有数据**——`Character.injury_level` 字段已删除
- **查询走 buff**——`InjuryService.get_injury_level(c)` 内部 = `BuffService.sum_attribute(c, "injury", "general_wound", "level")`
- **监控走 signal**——订阅 buff_applied/removed/attribute_changed，累计到 100% 时触发 ActionState DEAD
- **写入走 buff**——`InjuryService.apply_wound()` 内部走 BuffService 操作 injury buff
- 未来扩展（M5+）：拆细 subtype（中毒 / 外伤 / 经脉损伤），injury_level 改为 `sum_attribute_by_category("injury", "level")` 加权累加，**Character schema 不变**

#### M3 默认注册的 4 个 buff 类型

| Buff | 适用 target | M3 用途 |
|---|---|---|
| `injury/general_wound` | CHARACTER | 受伤综合载体（替代旧 injury_level 字段）|
| `cultivation/qi_acceleration` | CHARACTER, **SECT** | 灵气加速（角色或全宗门）|
| `cultivation/closed_door_decay` | CHARACTER | 闭关边际递减（§2.4）|
| `battle/wounded_aftermath` | CHARACTER | 战斗虚弱 |

### 6.11 宗门数据结构（用户定调 v3 · 实体 + IBuffable）

> ADR：[`adr/0006-sect-data-structure.md`](../adr/0006-sect-data-structure.md)（proposed）

宗门是真实的**有状态实体**，不是数据散落在各 service 的虚拟概念。

#### Sect 数据结构（关键字段）

```
Sect (实现 IBuffable)
├─ target_type: SECT
├─ buffs: Array[Buff]              # 可挂 SECT 类型 buff
├─ name / faction / reputation
├─ resources: Dict                 # 灵石 / 药材 / 法宝库存
├─ buildings: Array                # 建筑实例
├─ member_ids: Array[character_id] # 仅引用，不持有 Character 实例
├─ relations: Dict                 # 与各派系关系
└─ milestones: Array               # 大事记
```

#### 子领域服务的边界（§6.9 解耦应用）

- **SectService** —— Sect 数据的唯一入口（getter / setter / signal）
- **InventoryService** —— 物品 / 资源领域规则，**通过 SectService 读写**资源字段
- **BuildingService** —— 建筑领域规则（建造 / 升级公式），通过 SectService 读写建筑字段
- **ReputationService** —— 声望计算，通过 SectService 读写

#### 宗门 Buff 用例（关键设计点）

| Buff | 触发场景 | 效果 |
|---|---|---|
| `cultivation/qi_acceleration`（SECT）| 灵气潮汐事件 / 阵法 | 消费方 fan-out 到全宗门弟子修炼速度 |
| `environment/qi_richness`（SECT）| 宗门所在地灵气浓度 | 长期 buff，影响修炼 / 招收 |
| `external/under_attack`（SECT）| 邻宗来袭 | debuff 影响声望 / 阻建设 |
| `external/imperial_blessing`（SECT）| 主线大事件 | 加资源产出 |
| `internal/disciple_unrest`（SECT）| 弟子心性低 | 加叛门概率 |

> **fan-out 责任在消费方**：`qi_acceleration` 加成全宗门弟子是 ProductionService 监听宗门 buff_applied 后自己实现，BuffService 不感知 fan-out 逻辑。

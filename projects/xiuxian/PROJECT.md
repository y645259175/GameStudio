# xiuxian · 修仙宗门搜打撤退

## 一句话概述

你是一宗之主：在宗门内修炼、培养弟子、炼丹炼器、经营道场，亲自或派遣弟子外出秘境历练，带回资源以提升宗门实力，最终冲击飞升。

## 类型定位

**单机 2D 沙盒经营 + 选项式 extraction**
（参考混合：潜水员戴夫的双层循环节奏 × 鬼谷八荒的修仙世界观与水墨美术 × Tarkov-lite 的搜打撤退张力）

## 目标玩家

- 喜欢经营管理 + 探索决策的玩家
- 修仙 / 武侠题材爱好者
- 偏好节奏可控、单局可暂停的单机沙盒
- 平台：Steam（PC，Win 优先）

## 核心循环（一句话）

宗门内务（修炼/加工/培养，10-20 min）⇄ 外出历练（节点地图 + 选项事件，10-40 min）→ 资源回流加工 → 实力提升 → 解锁更深秘境。

## 玩法柱（三柱）

1. **宗门经营**（50%）—— 主世界，混合式（指令 + 关键事件小玩法），有边际递减促使外出
2. **外出历练**（50%）—— 小世界，门主亲征（节点地图 + 选项事件 + 战斗 + 撤退）/ 派遣弟子（黑盒消息流）
3. **角色与境界成长**（贯穿）—— 门主 / 弟子 / 长老统一数据结构，可继承传位

### 里程碑边界纪律（用户原话翻译 · 2026-05-23 二次定调）

1. **M1**：尽量列全所有未来系统的框架；**M1 之后允许加新系统**，但要走 GDD-01 §6.9.4 的 5 步预案
2. **M2**：实现必须参考 M1 完整规划；存档 / 数据位置一次到位；考虑未来加内容不爆存档
3. **M3**：玩法跑通 + 商业化基础美术（UI 视觉 / 插图 / 立绘）+ 5 件基本功能（主菜单 / 开始 / 结束 / 存档 / 读档）
4. **M4 ↔ M5 分离**：先扩内容（宗门内 + 大地图），再加主线剧情 + 战斗系统升级
5. **战斗系统**：M3 用数值对拼（StatSimulator），M5 升级为完整回合制 + 衍生技能/装备系统；接口在 M2 即落地

## 关键约束（"框架开放性"承诺）

> 用户强调：**项目整体的开发必须对后续内容的开放留出足够的框架；
> 提前安排好可扩展性，至少要提前知道可能出现的问题点；
> 程序方面要减少系统耦合以防出现各种关联 bug。**
>
> 已沉淀到 MEMORY.md 项目级约定，并在 GDD-01 §6 技术架构原则展开（9 节 + 风险预案）。

| 维度 | 必做 |
|---|---|
| 数据驱动 | 角色 / 物品 / 事件 / 地图 / 技能 / 装备 全部 JSON 或 Godot Resource |
| 战斗 | 抽象 `BattleResolver` 接口（M2 落地），M3 实现 `StatSimulator`（数值对拼），M5 升级为回合制 + 技能 / 装备 / 状态效果衍生系统 |
| 事件 | 选项→后果用数据/脚本描述，不写死 if-else 树 |
| 主线钩子 | `WorldEventTrigger` 接口 M2 建，钩子目录 M1 列全，剧情 M5 填 |
| 角色状态 | `state ∈ {MasterCurrent, Disciple, Elder, Dead, Injured, InClosedDoor}` 状态机统一处理；含 skills / equipped / status_effects 字段（M3 可空 / M5 启用）|
| 时间 | 单一 `TimeService` 总线，所有系统订阅 signal，不直读 |
| 存档 | M2 必做 5 点决策：版本号 / 数据分区 / get+default 兼容 / 未知字段保留 / 模板vs实例分离 |
| 系统解耦 | 通信只走 EventBus / Service 接口 / 只读 data；M1 必须画依赖矩阵（GDD-10）；跨 3+ 系统改动 commit 加 `[cross-system]` tag |
| 加新系统 | M1 之后允许，但走 5 步预案：ADR / 更 GDD-10 / 存档兼容 / 更依赖矩阵 / 接口检查 |

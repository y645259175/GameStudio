# M6.2 Retro · 美术资产管线踩坑总结

> bolt-1-1 第三轮用户反馈循环。表面是 4 个具体问题，根因是工作室级 SOP 缺失。

## 用户反馈（实质）

> "1. 还是太小，比例不对，跳起来都碰不到蘑菇
> 2. 没有待机动画
> 3. **idle 状态和运动状态都不是同一个人物了，你确定是生成的一套资源吗？**"

第 3 条是关键 —— "都不是同一个人物" 直接戳穿了 M6 美术接入的根本质量问题。

## 三条根因

### 根因 1 · 4 帧角色不一致（流程级失误）

**做错了什么**：用 `text2image.py` 跑了 4 个独立 prompt（idle / walk1 / walk2 / jump）期望"模型在 prompt 里看到 'same character' 就保持一致"。

**实际发生**：每帧出来 4 个完全不同的红色小怪 —— 一帧戴帽、一帧像红蜘蛛、一帧双色机器人。**gpt-image-2 在不同 API 调用之间没有任何共享状态**，prompt 里的 "same character" 是无效约束。

**正确做法（已经写进 SOP）**：
1. 先用 `text2image` 出 1 张 **canonical key sprite**（如 idle）
2. 用户 / art-director 评审通过后才能进 Step B
3. 所有其他帧用 `image_edit.py --image <key>.png` 派生（参考图带过去模型才知道角色长什么样）
4. **禁止**多帧并行 `text2image`（即使写 "same character"）

### 根因 2 · 透明背景 fallback（工具级）

**做错了什么**：相信了 prompt 里的 "transparent background" + 用了简单的 `remove_checkered_bg`（只看 corner 取平均色 + 距离阈值 30）。

**实际发生**：模型给的"透明背景"经常是 **画了 checkered 棕色图案** 当背景占位，alpha 全 255。距离阈值 30 太严格，去不掉。

**修复**：`postprocess.remove_checkered_bg` 改用 **flood-fill 从图片边缘洪泛 + 多色 bucket 量化**。能正确处理 checkered 双色背景。这是 PIL 算法层的固有改进，对所有项目通用。

### 根因 3 · 角色尺寸规范缺失（设计级）

**做错了什么**：随便写 16x16，没有从"屏幕占比 / 玩家可见性 / 比例感"反推合理尺寸。

**实际发生**：16x16 sprite 在 1280×720 视口占屏 1.25%，**远低于马里奥原作（16/240=6.7%）**。用户说"小到看不见"是直接的物理事实。

**修复（写进 art-asset-pipeline SKILL.md）**：「角色尺寸规范」表给出建议默认值：
- 主角 small 24×24（可调到 32×32）
- 主角 big / 高态 24×40（或 32×56）
- 普通敌人 24×24 ~ 28×32
- 道具 / icon 20×20
- Tile 32×32
- camera zoom 1.5x ~ 2x（视游戏类型）

## 二阶教训（工作室级）

| 失误模式 | 工作室级防御 |
|---|---|
| AI 即使写"same character"也没用 | art-asset-pipeline SKILL.md 强制 reference-based SOP |
| 模型给的"透明背景"实际是 checkered | postprocess flood-fill 算法常态化 |
| 单图 prompt 不知道目标尺寸 | SOP 加角色尺寸规范表，prompt 必带"占 X% 画布" |
| 限流时仍并发跑高量任务 | daemon.py concurrency 默认 3，限流时单任务串行重试 |
| 4 帧动画跑完才发现不一致 | SOP 第 1 步先要求 key sprite **用户评审通过**再进 Step B |

## 实际成本

- 浪费的 API 调用：第 1 轮 6 张失败 (RateLimit) + 第 2 轮 4 张 image_edit 都失败 (RateLimit)
- 浪费的等待时间：~30 分钟跑无效 retry
- 用户反馈循环：3 轮（第 1 轮"M6 PASS"→ 用户反馈 4 项 → 第 2 轮修了 3 项 → 用户反馈"还不是同一个人"→ 第 3 轮重做）

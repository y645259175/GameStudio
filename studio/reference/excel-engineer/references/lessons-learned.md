# 配表工程师实战经验教训

## Skill 库管理经验

### SVN 中文文件名提交失败（"not under version control"）：先检查控制台代码页

**场景**：用 Python 脚本/PowerShell 调 svn 提交中文文件名 xlsx，报 W155010 "node not found" 或 "not under version control"，但 `os.path.exists()` 明明返回 True、文件实际就在工作副本里
**根因**：当前控制台**活动代码页是 65001 (UTF-8)**，而非中文 Windows 默认的 936 (GBK)。PowerShell/Python subprocess 会按当前代码页编码命令行参数传给 svn.exe，svn.exe 按 GBK 解码 → 中文路径变乱码字节 → 找不到文件
**诊断方法**：终端执行 `chcp` 查看活动代码页。若是 65001 即触发本问题
**正确做法**：
- 提交脚本开头强制 `os.system('chcp 936 >nul 2>&1')`（Python）或 `chcp 936 | Out-Null`（PowerShell）
- 然后按 `svn-commit-workflow.md` 的标准模板正常走（绝对路径列表 + GBK log 文件 + `-F` 参数）
- 标准模板**经过几十次提交验证，是对的**，不要因为这个错误就怀疑模板
**禁止做的事**：
- 走 `--depth=immediates` 捷径绕过标准流程（log 会乱码，要 propset 救火，得不偿失）
- 用 `--targets` 文件传路径（仍受代码页影响）
- 凭空编造"Python subprocess 传参编码不可控""中文路径无解"等伪结论
**教训**：遇到 svn 中文路径异常，第一反应是 `chcp` 检查代码页，不是怀疑标准模板；不要为绕过问题而走捷径并把错误根因写进经验库

### 提交 Skill 到公共库必须同步更新 README.MD

**场景**：将 timiai-image skill 同步到公共库时，只提交了 Skill 文件夹，遗漏了 `README.MD` 的更新
**根因**：执行时只关注文件复制和 SVN commit，没有按照 `skill-incubation.md` 中的流程操作——该文档第 219 行已明确写明「README.MD 必须同步更新并一并提交」，流程文档本身是对的，是执行时没有遵守
**解决方案**：向公共库提交新 Skill 或更新 Skill 时，必须同步：① 更新公共库 `README.MD` 的 Skill 列表 ② 在同一次 commit 中一并提交（Skill 文件夹 + README.MD）
**教训**：有流程文档不等于会执行，提交前必须主动对照 `skill-incubation.md` 的步骤逐项检查

## Excel 操作经验

### 修改字段前必须检查公式引用关系

**场景**：将训练士兵的战斗力(fightvalue)清零后，导表发现 MilitaryExploitDeadBase/InjureBase/HurtBase 也跟着变了
**根因**：这些字段是公式（如 `=AB4*0.1`），直接引用了战斗力列，战斗力变 0 后公式结果联动变化
**解决方案**：修改任何字段值之前，先用 openpyxl（非 data_only 模式）扫描整个 Sheet，检查是否有其他单元格的公式引用了目标列。如有引用关系，必须在修改清单中列出并告知用户，让用户判断联动影响是否可接受
**教训**：不能只关注直接修改的字段，公式联动是隐性风险，必须主动排查和提示

### 字段名中括号标注分隔符规则

**场景**：读写 Excel 配置表多值字段时，需要判断实际填写的分隔符
**规则**：字段英文名中的中括号 `[]` 标注了该字段的**数据分隔符**，填写数据时必须使用中括号内标注的符号
**常见格式**：
- `fieldName[;]` → 分号 `;` 分隔的列表，如 `inherentSkillList[;]` → `200119;200117;200030`
- `fieldName[|]` → 竖线 `|` 分隔的列表，如 `buffSoldierTypes[|]`
- `fieldName[:]` → 冒号 `:` 分隔的列表，如 `defaultSkillList[:]`
- `fieldName[;]{key:value}` → 分号分隔 + 每项是键值对结构
- `fieldName[|]{key:value}` → 竖线分隔 + 键值对结构

**教训**：严格按照字段名中括号内的符号作为实际分隔符，不要自行推断或混淆

### openpyxl 保存复杂 Excel 会丢失数据（严重）

**场景**：用 openpyxl 打开英雄配置表修改 2 个 Sheet 的数据后保存
**问题**：openpyxl 保存时丢失了其他 Sheet 的大量数据——天赋树丢失 67542 行、新英雄开放控制丢失 1024 行、海外英雄标签丢失 202 行等。导出后所有 pbin/txt 都产生了严重差异，已提交到 SVN 后紧急回退
**根因**：openpyxl 无法完美处理复杂 Excel 文件（含公式、数据验证、条件格式、特殊结构等），保存时会静默丢弃它无法识别的内容
**解决方案**：修改 Excel 文件不能使用 openpyxl 直接保存整个 xlsx。应改用 COM 自动化（win32com）通过 Excel 应用程序操作，或让用户手动在 Excel 中修改
**教训**：openpyxl 只适合读取数据，不能用于保存项目中的复杂配置表。这是致命陷阱——保存时不会报错，但数据会静默丢失

### win32com 保存安全性已验证

**场景**：用 win32com 修改道具表、战斗表等多个复杂表后保存
**结论**：win32com 保存后文件大小变化 <0.01%，不丢失数据。是当前唯一安全的 Excel 写入方式
**对比**：openpyxl 保存同一文件会丢失 30% 数据，win32com 仅变化几十字节

### win32com 大表逐单元格读取极慢

**场景**：用 `ws.Cells(r, c).Value` 逐行遍历道具配置表（4696行）查找特定 id
**问题**：每次 `Cells` 访问都是一次 COM 跨进程调用，4696次循环耗时 34 秒
**解决方案**：使用 `ws.Range(...).Value` 一次性批量读取整个区域到 Python 数组，再用 Python 原生循环处理。参考 `scripts/excel-modify-template.py` 中的 `read_range()` 函数
**教训**：大表（>500行）必须用批量读取，禁止逐单元格遍历。小表（<100行）或只读几个固定单元格时可以逐个读取

### 禁止同时创建多个 Excel COM 实例

**场景**：测试中用两个 `Dispatch("Excel.Application")` 分别只读锁定和写入同一文件
**问题**：关闭第二个 Excel 进程时，第一个也被断连，抛出「被调用的对象已与其客户端断开连接」
**解决方案**：全局只维护一个 ExcelApp 实例，在同一个 with 块内完成所有读写操作。需要先读后写时，先只读打开读取数据→关闭 wb→再可写打开写入，不需要退出 Excel 进程
**教训**：多 COM 实例并存会互相干扰，这是 Windows COM 的已知行为

### 行号异常 / 数据非预期时，第一时间考虑用户手动整理过表

**场景**：完成一轮改表后被告知"还要再改"，二轮 probe 时发现某些行的位置/内容与上一轮记录的不一致
**可能根因（按概率从高到低）**：
1. ⭐ **用户手动整理了表格**（剪切粘贴、排序、插行删行）——开发期非常常见，例如把追加在末尾的新行剪切到对应类型的相邻位置
2. 别人提交了新内容（svn update 后位置变化）
3. 同一会话里上一轮 probe 是 openpyxl read_only 模式，缓存或行号判定与 win32com 不一致

**应对策略（不要每轮都重 probe，按需触发）**：
- **默认**沿用上轮 probe 结果（每轮重 probe 成本太高没必要）
- **只有当本轮看到的数据/位置与预期不符时**，立刻用 win32com 重 probe：
  ```python
  ws.UsedRange.Rows.Count
  ws.Cells(ws.Rows.Count, 1).End(-4162).Row  # xlUp = -4162
  ```
  并核对几个关键行的实际内容（id / type / 备注）
- **不要凭记忆继续写**——上轮位置可能已失效

**本次实例**：第二轮处理「7243→7244 顺延」前，发现"我新加的两行从 4721/4722 跑到了 4700/4701"。一开始误以为是 openpyxl/win32com 行号 bug，写了一长段排查计划，被用户澄清"是我手动剪切到了 7242 下面"——澄清后基于新位置改即可。

**教训**：行号异常 ≠ 工具 bug。**先怀疑用户做过整理**（最常见原因），再去查工具行为；不要急着写"工具不一致"的怀疑结论。

### 新增道具/英雄 id 必须先 probe 目标 id 段查重

**场景**：用户给出"用 7243/7244 这两个 id"做加速道具，本以为现网最大 id 是 50,501,014、7243 段位安全，写入后用户告知 7243 与「帝国之星 IT_RoadOfHonorStar」冲突，要求顺延。
**根因**：道具表 id 段**不是按 type 严格分段**，多个系统都会从某一段抢号（实测 7000 段同时被 IT_Common / IT_RoadOfHonorStar / IT_MarchSpeedUp 等多种 type 占用）。"最大 id+1"对避免冲突几乎没用。
**解决方案**：拿到任何指定 id（用户指定 / 策划文档 / 自己规划）后，**写入前必须用 win32com 或 openpyxl 全表扫一遍 id 列查重**：
```python
all_ids = {row[0] for row in rows[3:] if row and row[0]}
conflict = all_ids & {7243, 7244}
if conflict:
    print(f'⚠️ id 冲突：{conflict}')
    # 立即停下向用户报告，不要写入
```
**教训**：用户/策划/程序口头给出的 id 不能信，必须配表侧实证。命中冲突立即停下报告，不要"自动顺延"——顺延后的新 id 也可能再冲突，需用户决策。

### export_one_for_ai.py 遇现网脏数据会 SystemExit 整个挂掉

**场景**：导出本次新增的 IT_MarchSpeedUp 道具，被一个**与本次修改无关**的 IT_ChooseRewardBox 校验失败（"奖励id:49633，道具id:2300210，pbin:RewardConfData_23.pbin"）打断，ItemConfData.pbin 没生成
**根因**：`Converter.process()` 对 D_道具配置.xlsx 做全表交叉校验，遇到任何错误就 SystemExit（被 export_one_for_ai.py 捕获并退出），不能跳过单个错误继续
**判断"错是不是自己引入"**：
- 看错误信息里的 id/字段，与本次新增的对比
- 完全无关 → 99% 是别人的脏数据
- 有交叉 → 检查自己的字段填写
**遇到无关脏数据时的处理**：
- (a) 暂不导，向用户说明，等责任人修复后再导
- (b) 找到责任人请其修复
- (c) **不要**自行修复别人的脏数据（哪怕看似简单）——你不知道为什么这么配
**教训**：导表错误信息要先看"id 是不是自己加的"。遇到与自己无关的脏数据，向用户报告而不是绕过。

## SVN 提交经验

### 中文编码问题

**场景**：SVN 提交时 commit log 包含中文
**问题**：直接用 `-m` 参数传入中文 log，在 SVN 服务器上显示乱码
**解决方案**：将 log 写入 GBK 编码的临时文件，用 `-F` 参数传入
**教训**：本项目 SVN 服务器使用 GBK 编码存储 log，必须用 GBK 写入。不能用 UTF-8/UTF-8 BOM

### --story 参数冲突

**场景**：commit log 中包含 `--story=xxx` 格式的内容
**问题**：SVN 将 `--story` 解析为自己的命令行选项，导致提交失败
**解决方案**：通过 Python 脚本提交，log 写入文件用 `-F` 传入，避免被 shell 解析
**教训**：任何包含 `--` 前缀的 log 内容，都不能直接放在命令行中

### SVN 提交前必须展示清单并确认

**场景**：用户提供了 story 号和提交说明，直接执行了 svn commit
**问题**：跳过了"展示提交文件清单 + 确认"环节，依赖 IDE 审批弹窗代替了专家确认流程
**解决方案**：提交前必须：① 列出所有待提交文件 ② 展示 commit log ③ 明确询问用户确认。IDE 审批不能替代专家确认
**教训**：用户提供提交信息 ≠ 用户确认提交。两个是不同步骤，缺一不可

### 导表后只提交相关 Sheet 的产物

**场景**：修改了英雄配置表的"英雄"和"英雄进阶"两个 Sheet，导出后提交了整个 xlsx 所有 Sheet 的 pbin/txt（34个文件）
**问题**：导出工具按整个 xlsx 导出所有 Sheet，未修改的 Sheet 也被重新生成 pbin，SVN 检测为 Modified。全部提交导致提交记录包含无关文件
**解决方案**：导表后对比 SVN 变更列表，只提交与实际修改 Sheet 相关的 pbin/txt 文件，其余用 `svn revert` 还原
**教训**：导表 ≠ 全量提交。必须识别出真正变化的产物文件，避免污染提交记录

## 跨 Skill 协作经验

### 临时文件存放规则

**场景**：调试 Python 脚本时需要创建临时测试文件
**问题**：在项目根目录 `D:\Work\SLGX\` 下创建了 `_test.py`，污染了项目根目录
**解决方案**：所有临时文件（测试脚本、日志、调试文件等）必须严格放在 `common/excel/AI/temp/` 目录下
**教训**：绝对不能在项目根目录或其他任意位置创建文件。只有 `AI/temp/` 是合法的临时文件存放位置

### 引用工具找不到时的处理规则

**场景**：SKILL.md 或 references 中提到需要使用某个脚本/工具，但在预期位置找不到
**问题**：未经用户同意自行从零创建了替代导出脚本，手动调用 Converter API 踩了大量坑，导出结果有问题，用户花了几个小时排查
**解决方案**：找不到引用的工具时，**必须第一时间询问用户确认**——是脚本位置有误、还是需要创建、还是其他原因
**教训**：绝对不能未经用户同意就自行创建替代脚本。宁可停下来问，也不能闷头自己造轮子

### 子Skill缺失处理

**场景**：任务匹配到注册表中的子Skill，但本地找不到
**问题**：直接静默降级或自行处理，用户不知情
**解决方案**：先查公共Skill库（`common/excel/AI/skills/`）是否有该Skill → 有则询问安装 → 没有则告知用户提供A（自行处理）/B（用户解决）两个选项
**教训**：绝不静默降级，必须显式告知用户让用户决定

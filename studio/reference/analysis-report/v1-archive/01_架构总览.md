## 1. 产品定位与设计哲学

### 一句话是什么

CCGS 是一个"AI 游戏工作室模拟器"：用文档（Markdown）+ 提示词工程，在 Claude Code 单个会话里模拟一个有 49 名专业人员的完整游戏开发团队。

### 核心理念

CCGS 的设计围绕一个核心矛盾的解决：**AI 能力强大，但缺乏结构**。一个没有约束的 AI 会跳过设计文档直接写代码，忽视架构决策，在没有评审的情况下提交不一致的内容。

CCGS 的解决方案是：用**角色分工 + 工作流程序 + 自动化校验**，把 AI 的行为约束成"一个有自律的专业团队"。

### 三大设计原则

**原则 1 — 协作式，非自主式**

> 核心口号：*"You stay in control. The agents provide structure and expertise, not autonomy."*

所有 agent 遵循"五步协作协议"：
```
Ask（提问）→ Options（提供选项）→ Decision（用户决策）→ Draft（起草）→ Approval（获批再落笔）
```

Agent 是"专家顾问"，用户是"创意总监（最终决策者）"。Agent 绝不自主生成和提交，永远等用户批准。

**原则 2 — 文件即记忆**

> *"The file is the memory, not the conversation."*

会话历史是短暂的（会被压缩或丢失），文件是持久的。所有决策、设计、进度都落到磁盘文件。`production/session-state/active.md` 是会话检查点，任何崩溃后先读它来恢复状态。

**原则 3 — 验证驱动开发（Verification-Driven Development）**

所有实现都需要可证明的验证方式：游戏逻辑写单元测试，UI 变更截图确认，配置数据跑烟雾测试。不能 prove it works 的实现不算完成。

### 引用的游戏设计理论框架

| 框架 | 全称 | 在 CCGS 中的用途 |
|---|---|---|
| MDA | Mechanics-Dynamics-Aesthetics（机制-动态-美学） | 分析游戏设计、brainstorm 阶段用来拆解游戏体验 |
| SDT | Self-Determination Theory（自我决定理论） | 分析玩家动机：自主感/胜任感/归属感 |
| Flow State | 心流理论 | 挑战-技能平衡，保持玩家沉浸 |
| Bartle Types | 玩家类型理论（探险者/成就者/社交者/杀手） | 目标受众定位与验证 |

## 2. 三层角色（Agent）体系

### 一句话是什么

49 个 agent 按能力强度分三层，类似真实工作室的"总监 → 部门主管 → 专员"层级，决策向上汇报，执行向下委派。

### 体系总图

```
[用户]（最终决策者，不可绕过）
    |
    ├── Tier 1 — Directors（总监级，3+1 个，Opus 模型）
    │   ├── creative-director    创意总监：游戏愿景、支柱、创意冲突裁决
    │   ├── technical-director   技术总监：架构决策、技术风险、性能预算
    │   └── producer             制作人：排期、里程碑、跨部门协调
    │   ＊art-director 虽在 Gates 文档被列为 Tier 1 级 Gate 主体，但在 agent-roster 中归为 Tier 2
    |
    ├── Tier 2 — Department Leads（部门负责人，8 个，Sonnet 模型）
    │   ├── game-designer         游戏设计主管：核心循环、系统设计、GDD
    │   ├── lead-programmer       首席程序员：代码架构、接口约定、代码审查
    │   ├── art-director          美术总监：视觉风格、美术圣经、资产标准
    │   ├── audio-director        音频总监：音乐方向、音效调色板
    │   ├── narrative-director    叙事总监：故事弧、世界构建、对话策略
    │   ├── qa-lead               QA 负责人：测试策略、Bug 分级、发布就绪度
    │   ├── release-manager       发布经理：构建管理、版本控制、变更日志
    │   └── localization-lead     本地化负责人：字符串外化、翻译流程
    |
    └── Tier 3 — Specialists（专员，38 个，Sonnet/Haiku 模型）
        ├── 通用专员（24 个）
        │   systems-designer / level-designer / economy-designer
        │   gameplay-programmer / engine-programmer / ai-programmer
        │   network-programmer / tools-programmer / ui-programmer
        │   technical-artist / sound-designer / writer / world-builder
        │   ux-designer / prototyper / performance-analyst / devops-engineer
        │   analytics-engineer / security-engineer / qa-tester
        │   accessibility-specialist / live-ops-designer / community-manager
        │
        ├── Godot 4 专员组（5 个）
        │   godot-specialist → godot-gdscript-specialist
        │                    → godot-shader-specialist
        │                    → godot-gdextension-specialist
        │                    → godot-csharp-specialist
        │
        ├── Unity 专员组（5 个）
        │   unity-specialist → unity-dots-specialist
        │                    → unity-shader-specialist
        │                    → unity-addressables-specialist
        │                    → unity-ui-specialist
        │
        └── Unreal Engine 5 专员组（5 个）
            unreal-specialist → ue-gas-specialist
                              → ue-blueprint-specialist
                              → ue-replication-specialist
                              → ue-umg-specialist
```

> **注意**：`art-director` 在 `agent-roster.md` 中归为 Tier 2 Leads，但在 `director-gates.md` 中被列为与三位 Tier 1 总监平行的 Gate 主体（AD-CONCEPT-VISUAL / AD-ART-BIBLE / AD-PHASE-GATE）。实践中，`art-director` 在创意决策上具有接近 Tier 1 的权威，但使用 Sonnet 而非 Opus 模型。

### 模型分层路由

不同 agent/skill 依据任务复杂度使用不同的 AI 模型，以平衡质量与成本：

| 模型 | 对应任务 | 典型使用场景 |
|---|---|---|
| **Haiku**（最快最省） | 只读状态检查、格式化、简单查询，不需要创意判断 | `/help`、`/sprint-status`、`/project-stage-detect`、`/changelog`、sound-designer、qa-tester、devops-engineer |
| **Sonnet**（默认主力） | 实现、设计起草、单系统分析 | 大多数 skill 和 Tier 2/3 agent |
| **Opus**（最强最贵） | 多文档综合分析、高风险阶段门控裁决、跨系统整体评审 | Tier 1 Directors（creative/technical/producer）；`/review-all-gdds`、`/architecture-review`、`/gate-check` |

**创建新 skill 的选择规则**（来自 `coordination-rules.md`）：
- 只读取并格式化 → 指定 Haiku
- 需要综合 5+ 个文档并给出高风险结论 → 指定 Opus
- 其余 → 不指定，默认 Sonnet

### Memory（记忆）策略

| 类型 | 作用 | 使用范围 |
|---|---|---|
| `memory: user` | 跨会话记住与用户的偏好、历史决策 | Tier 1 Directors（creative/technical/producer）—— 需要了解用户风格和长期决策 |
| `memory: project` | 跨会话记住当前项目的状态 | 14 个角色：art-director / audio-director / economy-designer / game-designer / gameplay-programmer / lead-programmer / level-designer / narrative-director / systems-designer / technical-artist / ui-programmer / ux-designer / world-builder / prototyper |
| 无 memory 声明 | 仅当前会话有效 | 其余 agent（Tier 1 之外的非上述 14 个） |

**重要**：CodeBuddy 当前不支持 `memory: project`（只有全局 Memory），移植后这 14 个角色的"项目记忆"需用 CODEBUDDY.md + Rules 替代，详见 01b 册 P2。

## 3. 五种协调规则

### 一句话是什么

明确规定 agent 之间如何传递任务和解决分歧，防止 AI 互相打架或越权决策。

| 规则 | 通俗解释 | 技术说明 |
|---|---|---|
| **垂直委派** | 上级把任务交给下属，不能越级 | Director → Lead → Specialist，复杂决策不跳级 |
| **水平咨询** | 同级可以互相问意见，但不能替对方做决定 | 同 Tier agent 可 consult，不可 bind cross-domain decisions |
| **冲突上升** | 两个 agent 意见不一致时，去找共同上级裁决 | 设计冲突 → creative-director；技术冲突 → technical-director |
| **变更传播** | 跨部门的改动要由 producer 协调通知相关方 | design change → notify lead-programmer + qa-lead + producer |
| **域边界** | agent 不能动自己职责范围以外的文件 | 没有明确授权不能跨目录操作 |

### 委派完整关系图

| 委派方 | 可委派给 |
|---|---|
| creative-director | game-designer, art-director, audio-director, narrative-director |
| technical-director | lead-programmer, devops-engineer, performance-analyst, technical-artist（技术决策） |
| producer | 任何 agent（仅限其域内任务分配） |
| game-designer | systems-designer, level-designer, economy-designer |
| lead-programmer | gameplay/engine/ai/network/tools/ui-programmer |
| art-director | technical-artist, ux-designer |
| audio-director | sound-designer |
| narrative-director | writer, world-builder |
| qa-lead | qa-tester |
| release-manager | devops-engineer（发布构建）、qa-lead（发布测试） |
| [engine]-specialist | 对应引擎子专员 |

### 升级路径（冲突由谁裁决）

| 冲突场景 | 升级至 |
|---|---|
| 两个设计师对某机制意见不同 | game-designer |
| 游戏设计 vs 叙事内容冲突 | creative-director |
| 游戏设计 vs 技术可行性冲突 | producer 协调 → creative-director + technical-director |
| 美术 vs 音频的风格冲突 | creative-director |
| 代码架构争议 | technical-director |
| 排期冲突 | producer |
| 质量门控争议 | qa-lead → technical-director |
| 性能预算超标 | performance-analyst 标记 → technical-director 决策 |

## 4. 五步协作协议（The Collaboration Protocol）

### 一句话是什么

所有 agent 与用户互动时必须遵守的工作节奏，防止 AI 自作主张直接写代码或文件。

```
1. Ask（提问）     — agent 先问清楚背景，不猜不假设
2. Options（选项） — 提供 2-4 个有利弊分析的方案，而非单一"最优解"
3. Decision（决策）— 用户选择，agent 等待，不催促不引导
4. Draft（起草）   — 基于用户决策起草内容，展示给用户
5. Approval（批准）— 明确问"May I write this to [filepath]?"，只有用户说 Yes 才落笔
```

**关键机制：`AskUserQuestion` 工具**（Explain → Capture 模式）：

1. 先在对话中写完整的专家分析（利弊/理论/参考游戏/Pillar 对齐）
2. 再调用 `AskUserQuestion` 工具，以 UI 表单形式呈现精简的选项（标签 1-5 字，描述 1 句话）
3. 推荐选项标注"（Recommended）"

这个工具相当于 CCGS 版的"用户决策界面"，是协作协议的技术载体。

**增量文件写入策略**（防止长会话上下文爆炸）：

多节文档（GDD/ADR/架构文档）采用"先建骨架，逐节填充，每节落盘"的方式：
- Step 1：创建文件，写入所有节标题（空正文）
- Step 2：每次只讨论一节，得到批准后立即写入该节
- Step 3：已写入的节从会话上下文中淡出（信息在文件里了）
- 好处：8 节 GDD 的 30-50k token 对话压缩为每节 3-5k token 的滚动窗口

## 5. 七阶段生产 Pipeline

### 一句话是什么

CCGS 把游戏开发切成 7 个阶段，每个阶段都有必须完成的"门控文件"才能进入下一阶段，类似工厂流水线上的质量检查站。

### 阶段总览

| 阶段编号 | 阶段名 | 核心产出 | 硬性前置文件 |
|---|---|---|---|
| 1 | **Concept（概念）** | 游戏概念文档 + 引擎配置 + 美术圣经 + 系统地图 | `design/gdd/game-concept.md`、`.claude/docs/technical-preferences.md`（引擎已配置）、`design/art/art-bible.md`、`design/gdd/systems-index.md` |
| 2 | **Systems Design（系统设计）** | 每个系统一份 GDD，全量 GDD 交叉审查报告 | `design/gdd/` 下各系统 GDD（每份 Status: Approved）、`design/gdd/gdd-cross-review-*.md` |
| 3 | **Technical Setup（技术搭建）** | 主架构文档 + ≥3 份 ADR + 架构评审 + 控制清单 + 无障碍需求文档 | `docs/architecture/architecture.md`、`docs/architecture/adr-*.md`（≥3 份）、`docs/architecture/architecture-review-*.md`、`docs/architecture/control-manifest.md`、`design/accessibility-requirements.md` |
| 4 | **Pre-Production（预制作）** | UX 规范 + 原型 + Epics + Stories + Sprint 计划 + 首次游玩测试 | `design/ux/*.md`（≥1份）、`prototypes/*/README.md`（≥1份）、`production/epics/*/EPIC.md`（≥1份）、`production/sprints/sprint-*.md`（≥1份）、`production/playtests/*.md`（≥1份）|
| 5 | **Production（生产）** | Sprint 循环开发（拾取 Story → 实现 → Story Done） | `src/` 下有代码 + `production/epics/**/*.md` 中有 In Progress stories |
| 6 | **Polish（打磨）** | 性能优化 + 游戏平衡 + 多轮游玩测试（≥3次） + 团队打磨通道 | `production/playtests/*.md`（≥3份） |
| 7 | **Release（发布）** | 发布清单 + 发布说明 + 最终发布 | 发布清单全部通过 |

### 关键文件：`workflow-catalog.yaml`

这是整个 pipeline 的机器可读定义，由 `/help` 命令读取，告诉 AI：
- 当前项目在哪个阶段（通过检测文件是否存在来自动判断）
- 下一步必须/可选做什么
- 每一步对应的斜杠命令是什么

**必须（required: true）vs 可选（required: false）的区别**：
- `required: true` 的步骤必须完成才能推进；`/gate-check` 会把缺失的必须步骤列为阻塞项
- `required: false` 的步骤是推荐的增强，跳过不阻塞

**repeatable: true** 的步骤（如 `/design-system`、`/dev-story`）可以多次执行，每次针对一个新的系统或故事。

### 阶段自动检测（`statusline.sh`）

状态栏脚本通过以下规则自动判断当前阶段（优先级从高到低）：
1. 读取 `production/stage.txt`（若存在，优先用它）
2. `src/` 下源文件 ≥ 10 → Production
3. `docs/architecture/adr-*.md` 存在 → Pre-Production
4. `.claude/docs/technical-preferences.md` 引擎已配置 → Technical Setup
5. `design/gdd/systems-index.md` 存在 → Systems Design
6. `design/gdd/game-concept.md` 存在 → Concept
7. 以上均无 → Concept

## 6. Director Gates（总监关卡）系统

### 一句话是什么

工作流关键节点上自动召唤"总监"来审核当前决策，防止在没有充分思考的情况下草率进入下一阶段。就像手术前要做术前检查，总监关卡是质量防线。

### 为什么需要 Gates

CCGS 的 skill 原本把总监审核的提示词直接写在 skill 文件里，导致：
- 同一个审核提示在多个 skill 里重复，一处改动要多处同步
- 不同 skill 的同类审核行为不一致

v1.0 引入 Director Gates 系统：把审核提示词集中定义在 `.claude/docs/director-gates.md`，skill 只引用"门控 ID"（如 `CD-PILLARS`），不再内嵌提示词。

### 全部 Gates 目录

**Tier 1 — Creative Director（CD-）**

| Gate ID | 触发时机 | 审核重点 | 判定结果 |
|---|---|---|---|
| `CD-PILLARS` | 游戏支柱定义后 | 支柱是否可证伪、有差异化 | APPROVE / CONCERNS / REJECT |
| `CD-GDD-ALIGN` | GDD 起草后 | 系统设计是否服务于支柱 | APPROVE / CONCERNS / REJECT |
| `CD-SYSTEMS` | `/map-systems` 完成后 | 系统分解是否保留核心体验 | APPROVE / CONCERNS / REJECT |
| `CD-NARRATIVE` | 叙事内容生成后 | 叙事与游戏风格/世界观一致性 | APPROVE / CONCERNS / REJECT |
| `CD-PLAYTEST` | 游玩测试报告生成后 | 玩家体验是否符合预期幻想 | APPROVE / CONCERNS / REJECT |

|---|---|---|---|
| `AD-CONCEPT-VISUAL` | 游戏支柱锁定后（并行 CD-PILLARS） | 2-3 个视觉方向提案 | CONCEPTS / STRONG / CONCERNS |
| `AD-ART-BIBLE` | `/art-bible` 完成后 | 美术圣经完整性与一致性 | APPROVE / CONCERNS / REJECT |
| `AD-PHASE-GATE` | `/gate-check` 时（必须） | 视觉层面的阶段就绪度 | READY / CONCERNS / NOT READY |

**Tier 2 Lead Gates（LP- / QL- / ND- / AD-）**

| Gate ID | 主体 | 触发时机 | 判定结果 |
|---|---|---|---|
| `LP-FEASIBILITY` | lead-programmer | 架构文档完成后 | FEASIBLE / CONCERNS / INFEASIBLE |
| `LP-CODE-REVIEW` | lead-programmer | Story 实现后 | APPROVE / CONCERNS / REJECT |
| `QL-STORY-READY` | qa-lead | Story 进入 Sprint 前 | ADEQUATE / GAPS / INADEQUATE |
| `QL-TEST-COVERAGE` | qa-lead | Epic 完成或 Production→Polish 门控时 | ADEQUATE / GAPS / INADEQUATE |
| `ND-CONSISTENCY` | narrative-director | 叙事内容生成后 | APPROVE / CONCERNS / REJECT |
| `AD-VISUAL` | art-director | 美术方向决策后 | APPROVE / CONCERNS / REJECT |

### 三档评审强度（Review Mode）

CCGS v1.0 引入"评审强度"，允许根据开发阶段和团队偏好灵活调整总监参与程度：

| 强度 | 内容 | 适合场景 |
|---|---|---|
| `full` | 所有 Gates 全部激活 | 多人团队、学习阶段、需要充分导向 |
| `lean` | 仅 PHASE-GATE（`/gate-check` 时）激活，per-skill 内联 gate 跳过 | **CCGS 原默认**，独立开发者和小团队 |
| `solo` | 所有 Gate 均跳过，仅检查文件是否存在 | Game jam、原型阶段、极速推进 |

> **CodeBuddy 移植后建议**：由于 CodeBuddy 不支持并行 subagent，per-skill 内联 gate 的代价显著上升。移植后建议默认改为接近 `solo`（关键节点手动调用门控），详见 01b 册 P0。

**配置方式**：
- 全局配置：写入 `production/review-mode.txt`（内容为 `full` / `lean` / `solo` 之一）
- 单次覆盖：在任何支持 gate 的 skill 命令后加 `--review [mode]`，例如 `/brainstorm my-idea --review full`

**门控检查算法**（在任何 skill 内调用 gate 前执行）：
```
1. 若 skill 以 --review [mode] 调用，使用该 mode
2. 否则读取 production/review-mode.txt
3. 否则默认为 lean
4. 应用：
   solo → 跳过所有 gate，记录"[GATE-ID] skipped — Solo mode"
   lean → 跳过所有 gate，除非是 PHASE-GATE（CD/TD/PR/AD-PHASE-GATE）
   full → 正常 spawn
```

### 并行门控协议

> **CodeBuddy 适配警告**：以下并行机制是 CCGS 的原生设计，**在 CodeBuddy 上不可直接使用**（CodeBuddy 当前不支持 Skill 内并行 spawn subagent）。本节描述 CCGS 的原始设计意图，移植方案见 01b 册第一章 P0。

`/gate-check` 时 4 个总监级 Gate 必须并行触发（同时发出所有 Task 调用，不等待先出结果）：
```
并行 spawn：
  1. creative-director  → CD-PHASE-GATE
  2. technical-director → TD-PHASE-GATE
  3. producer           → PR-PHASE-GATE
  4. art-director       → AD-PHASE-GATE

收集全部 4 个判定后，应用"最严格优先"原则：
  任一 NOT READY/REJECT → 整体判定至少为 FAIL
  任一 CONCERNS         → 整体判定至少为 CONCERNS
  全部 READY/APPROVE    → 才有资格 PASS（但仍需检查文件是否存在）
```

### Gate 判定结果标准格式

所有 gate 返回三种判定之一，技能必须处理全部三种：

| 判定 | 含义 | 技能处理方式 |
|---|---|---|
| **APPROVE / READY** | 无问题，继续 | 继续工作流 |
| **CONCERNS [清单]** | 有问题但不阻塞 | 通过 `AskUserQuestion` 呈现给用户：修复 / 接受继续 / 进一步讨论 |
| **REJECT / NOT READY [阻塞项]** | 阻塞性问题 | 呈现阻塞原因，不写文件，不推进阶段 |

门控结果记录格式（写在相关文档的状态头部）：
```markdown
> **[Director] Review ([GATE-ID])**: APPROVED [日期] / CONCERNS (accepted) [日期] / REVISED [日期]
```

### 一句话是什么

项目有明确的目录规划，哪类文件放哪里是固定的，不能随意混放。AI 的 Rules（规范）也是按目录路径来激活的。

│   ├── rules/                     11 个编码/文档规范（按路径 glob 激活）
│   ├── docs/                      工作室文档（协调规则/workflow-catalog/模板等）
│   │   └── templates/             39 个文档模板（GDD/ADR/Sprint/UX/HUD等）
│   ├── agent-memory/              Agent 跨会话持久记忆
│   ├── settings.json              Hook 注册 + 权限规则 + 状态栏配置
│   └── statusline.sh              7 阶段面包屑状态栏脚本
│
├── src/                           游戏源代码（core/gameplay/ai/networking/ui/tools）
├── assets/                        游戏资产（art/audio/vfx/shaders/data）
├── design/                        设计文档（gdd/narrative/levels/balance/ux/art）
│   └── CLAUDE.md                  design/ 目录的 path-scoped 指令
├── docs/                          技术文档（architecture/ADR/engine-reference）
│   ├── CLAUDE.md                  docs/ 目录的 path-scoped 指令
│   └── engine-reference/          引擎 API 快照（版本锁定，防 API 漂移）
├── tests/                         测试套件（unit/integration/performance/playtest）
├── tools/                         构建与管线工具（ci/build/asset-pipeline）
├── prototypes/                    原型代码（与 src/ 完全隔离，可丢弃）

这三个文件在 AI 读取对应目录下的文件时自动加载，无需在主 CLAUDE.md 中手动引用。

## 8. 编码与设计标准摘要

### 代码标准（`coding-standards.md`）

| 类型 | 核心规则 |
|---|---|
| **代码文档** | 所有公开 API 必须有文档注释 |
| **架构追踪** | 每个系统必须有对应的 ADR |
| **数据驱动** | 游戏数值必须放外部配置文件，不可硬编码 |
| **可测试性** | 所有公开方法必须可单元测试（使用依赖注入，不用单例） |
| **提交规范** | 提交信息必须引用设计文档或任务 ID |
| **验证驱动** | 先写测试，再实现；UI 用截图验证；对比预期与实际输出 |

### 设计文档标准（8 必要节）

每份 GDD（游戏设计文档）必须包含：
1. Overview（概述）
2. Player Fantasy（玩家幻想/预期体验）
3. Detailed Rules（详细规则）
4. Formulas（公式，所有数学明确定义）
5. Edge Cases（边界条件处理）
6. Dependencies（依赖的其他系统）
7. Tuning Knobs（可调节参数列表）
8. Acceptance Criteria（可验证的验收标准）

### 测试标准（按故事类型）

| 故事类型 | 必须的测试证据 | 位置 | 严格程度 |
|---|---|---|---|
| **Logic**（公式/AI/状态机） | 自动化单元测试，必须通过 | `tests/unit/[system]/` | 阻塞性 |
| **Integration**（多系统交互） | 集成测试 OR 文档化游玩测试 | `tests/integration/[system]/` | 阻塞性 |
| **Visual/Feel**（动画/VFX/手感） | 截图 + 负责人签字 | `production/qa/evidence/` | 建议性 |
| **UI**（菜单/HUD/界面） | 手动步骤文档 OR 交互测试 | `production/qa/evidence/` | 建议性 |
| **Config/Data**（数值平衡） | 烟雾测试通过 | `production/qa/smoke-[date].md` | 建议性 |

## 9. 上下文管理策略

### 一句话是什么

在 AI 会话中，"上下文窗口"相当于工作记忆，满了就会遗忘。CCGS 用文件来做持久记忆，用分层写入来控制上下文用量。

### 关键策略

**文件是记忆，对话是暂存**：任何重要决策、设计、进度都立即写入文件。会话历史可以被压缩或丢失，文件不会。

**Session State 文件**：`production/session-state/active.md` 是"工作台日志"，记录：当前任务、完成清单、关键决策、正在编辑的文件、未解决的问题。每次重要里程碑后更新。

**状态栏面包屑**（Production/Polish/Release 阶段）：
当 `active.md` 中有如下结构时，状态栏显示 `Production | Combat System > Melee Combat > Hitboxes`：
```markdown
<!-- STATUS -->
Epic: Combat System
Feature: Melee Combat
Task: Implement hitbox detection
<!-- /STATUS -->
```

**主动压缩**：在上下文使用率达 60-70% 时主动执行 `/compact`，而不是等到 100% 被迫压缩。推荐压缩指令：`/compact Focus on [当前任务] — sections 1-3 写入文件，正在处理 section 4`

**按任务分配上下文预算**：
- 轻量（阅读/审查）：约 3k tokens
- 中量（实现一个功能）：约 8k tokens
- 重量（多系统重构）：约 15k tokens

**Subagent 委托**（用于隔离研究任务）：跨多个文件的调查、代码探索等，用 subagent 完成，只把摘要返回主会话，不把所有文件内容塞进主 context。

## 10. settings.json — 权限与 Hook 注册

### 一句话是什么

这是整个工作室的"规章制度文件"，声明了哪些操作被允许、哪些被禁止、以及在什么时机自动执行哪个检查脚本。

### 权限规则

**自动允许（allow）**：
- `git status / diff / log / branch / rev-parse`（安全的 Git 查看操作）
- `ls / dir`（目录列表）
- `python -m json.tool`（JSON 格式验证）
- `python -m pytest / py -m pytest`（运行测试）

**自动拒绝（deny）**：
- `rm -rf *`（危险删除）
- `git push --force / git push -f`（强制推送）
- `git reset --hard`（强制重置）
- `git clean -f`（强制清理）
- `sudo *`（提权操作）
- `chmod 777*`（危险权限修改）
- 读写 `.env` 文件（保护密钥）

### Hook 注册总览

| 事件 | Hook 脚本 | 通俗描述 |
|---|---|---|
| `SessionStart` | `session-start.sh` | 会话开始时：显示当前分支和最近提交，用于定向 |
| `SessionStart` | `detect-gaps.sh` | 会话开始时：检测空白项目（建议运行 `/start`）和文档缺失 |
| `PreToolUse` (Bash) | `validate-commit.sh` | 每次执行 bash 命令前：若是 `git commit`，检查硬编码值/TODO 格式/JSON 有效性 |
| `PreToolUse` (Bash) | `validate-push.sh` | 每次执行 bash 命令前：若是 `git push`，警告受保护分支 |
| `PostToolUse` (Write/Edit) | `validate-assets.sh` | 每次写文件后：若文件在 `assets/`，检查命名规范和 JSON 结构 |
| `PostToolUse` (Write/Edit) | `validate-skill-change.sh` | 每次写文件后：若修改了 `.claude/skills/` 下的文件，提醒运行 `/skill-test` |
| `Notification` | `notify.sh` | 收到通知时：在 Windows 显示 Toast 通知（PowerShell） |
| `PreCompact` | `pre-compact.sh` | 会话压缩前：保存当前 session 进度笔记 |
| `PostCompact` | `post-compact.sh` | 会话压缩后：提醒从 `active.md` 恢复状态 |
| `Stop` | `session-stop.sh` | 会话结束时：归档 `active.md` 到日志，记录 Git 活动 |
| `SubagentStart` | `log-agent.sh` | 子 agent 启动时：记录审计日志（子 agent 调用开始） |
| `SubagentStop` | `log-agent-stop.sh` | 子 agent 停止时：完成审计日志（子 agent 调用结束） |

**重要说明**：`validate-commit.sh`、`validate-assets.sh`、`validate-skill-change.sh` 在每次 Bash/Write 工具调用时都会触发，但它们在首行检查命令/路径是否相关，不相关时立即退出（exit 0），性能开销极小。

## 11. CCGS Skill Testing Framework（元测试框架）

### 一句话是什么

这是"给工具箱本身做检查的工具"——专门用于验证 CCGS 的 72 个 skill 和 49 个 agent 是否符合规范，而不是用于测试游戏本身。

### 框架结构

```
CCGS Skill Testing Framework/
├── catalog.yaml           所有 72 skill + 49 agent 的覆盖度追踪表
├── quality-rubric.md      按类别的 PASS/FAIL 评判标准（9 个 skill 类别 + 6 个 agent 类别）
├── skills/                每个 skill 的行为规格文件（spec），按类别组织
│   ├── gate/              gate-check 的规格
│   ├── review/            审查类 skill 的规格
│   ├── authoring/         创作类 skill 的规格
│   ├── readiness/         就绪检查类 skill 的规格
│   ├── pipeline/          流水线类 skill 的规格
│   ├── analysis/          分析类 skill 的规格
│   ├── team/              团队编排类 skill 的规格
│   ├── sprint/            Sprint 类 skill 的规格
│   └── utility/           工具类 skill 的规格
└── agents/                每个 agent 的行为规格文件，按层级组织
    ├── directors/ leads/ specialists/ godot/ unity/ unreal/ operations/ creative/
```

> **注意**：此框架是可选的，完全独立于 `.claude/` 目录。删除整个文件夹不影响 CCGS 正常工作。

### 测试命令

| 命令 | 用途 |
|---|---|
| `/skill-test static [skill-name]` | 7 项结构性合规检查（frontmatter 字段、必须节等） |
| `/skill-test static all` | 对全部 72 个 skill 批量运行结构检查 |
| `/skill-test spec [skill-name]` | 对照行为规格文件评估 skill 是否按预期工作 |
| `/skill-test category [name]` | 对照质量评判标准评估某类别的 skill |
| `/skill-test category all` | 对所有类别 skill 运行评判标准检查 |
| `/skill-test audit` | 生成覆盖度全景图（哪些有规格、上次测试时间、结果） |
| `/skill-improve [skill-name]` | 测试 → 诊断 → 提议修复 → 复测的闭环改进循环 |

### 9 大 Skill 类别的核心评判标准

| 类别 | 代表 skill | 最重要的合规要求 |
|---|---|---|
| `gate` | gate-check | 读取 review-mode；full 模式时 4 个总监并行；solo 时无 gate；不自动推进阶段 |
| `review` | design-review, architecture-review | 只读分析；检查 8 必要节；正确的判定词汇；有结构化发现表格 |
| `authoring` | design-system, ux-design, art-bible | 逐节创作；每节写前问"May I write"；先建骨架；有 retrofit 模式 |
| `readiness` | story-readiness, story-done | ≥3 个维度检查；三档判定（READY/NEEDS WORK/BLOCKED）；完成后推荐下一个 Story |
| `pipeline` | create-epics, create-stories, dev-story | 正确的输出 schema；尊重层级/优先级顺序；每个文件写前单独获批 |
| `analysis` | consistency-check, balance-check | 只读分析阶段；有结构化发现表；不自动写修复；不召唤总监 |
| `team` | team-combat, team-narrative 等 | 明确列出召唤的 agent；独立任务并行；阻塞立即上报；未提供参数时输出用法提示 |
| `sprint` | sprint-plan, sprint-status | 读取 `production/sprints/`；正确的 PR-SPRINT gate；结构化输出（表格/列表） |
| `utility` | start, adopt, hotfix 等 | 通过全部 7 项静态检查；有 gate 时 gate 逻辑正确 |

## 12. 三引擎分化策略

### 一句话是什么

CCGS 同时支持三个主流游戏引擎，且针对每个引擎有专属的"专家组"，避免用错引擎的 API 或工作流。

| 引擎 | 主专员 | 子专员（专攻领域） |
|---|---|---|
| **Godot 4** | `godot-specialist` | gdscript-specialist / shader-specialist / gdextension-specialist / csharp-specialist |
| **Unity** | `unity-specialist` | dots-specialist / shader-specialist / addressables-specialist / ui-specialist |
| **Unreal Engine 5** | `unreal-specialist` | gas-specialist / blueprint-specialist / replication-specialist / umg-specialist |

**引擎选择后的行为**：
- 运行 `/setup-engine [engine] [version]`，将引擎、语言、命名规范、性能预算写入 `.claude/docs/technical-preferences.md`
- 状态栏随之更新为"Technical Setup"阶段
- 所有代码相关 skill 和 agent 开始引用对应引擎的规范

**引擎版本风险管理**（`TD-ENGINE-RISK` gate）：
- `docs/engine-reference/` 存有各引擎的 API 快照（版本锁定）
- 引擎专员在建议任何 API 调用前，必须与版本参考对照，标注"知识截止日期"后的风险

## 章末：架构层面 CodeBuddy 适配性总评

> 以下结论均基于 CodeBuddy 官方文档（最后更新：2026-05-08）核实，无"待确认"项。

| 架构模块 | 适配性 | 核实结论 |
|---|---|---|
| **设计哲学（五步协作协议）** | 直接移植 | 纯思想/行为约束，无平台依赖；直接写入 CodeBuddy 的 Subagent/CODEBUDDY.md 提示词 |
| **三层角色体系（层级设计）** | 直接移植 | 角色分工和委派规则是纯文档概念，与平台无关 |
| **七阶段 Pipeline（workflow-catalog.yaml）** | 改造移植 | 数据结构可保留；读取逻辑需改为 CodeBuddy 自定义斜杠命令（`.codebuddy/commands/`） |
| **Director Gates 系统** | 改造移植 | 提示词文本可直接复用（这部分是直接移植的）；触发机制需用 CodeBuddy Subagents（agentic 模式自动 spawn）替代 Claude Code 的 Task tool。**重要**：CodeBuddy 当前不支持并行 subagent，原 CCGS 的"并行 Gate 协议"必须改为串行，详见 01b 册 P0 |
| **评审强度模式（full/lean/solo）** | 直接移植 | 纯配置文件约定，可原样保留 |
| **模型分层路由（Haiku/Sonnet/Opus）** | 改造移植 | CodeBuddy 支持通过 `.codebuddy/models.json` 配置多模型（支持 OpenAI/DeepSeek/Ollama/自定义 API）；可用"轻量模型"/"标准模型"/"重量模型"三档替代 Haiku/Sonnet/Opus，但无法在 agent frontmatter 里直接声明使用哪个模型 |
| **Memory 策略（user/project 分级）** | 改造移植 | CodeBuddy Memory 只有全局级别（等同于 user memory），无独立的 project-level memory。项目级记忆建议改用 Rules（`.codebuddy/rules`）替代 `memory: project` 的功能 |
| **settings.json 权限规则** | 改造移植 | CodeBuddy 使用同名 `.codebuddy/settings.json` 配置 Hooks，格式高度兼容（相同的 JSON 结构：hooks → 事件 → matcher → command）；权限 allow/deny 规则需用 Hook PreToolUse 的 `permissionDecision: deny` 替代 |
| **Hook 事件系统（12 个）** | 改造移植 | CodeBuddy 支持 7 种 Hook 事件（SessionStart/SessionEnd/PreToolUse/PostToolUse/UserPromptSubmit/Stop/PreCompact），覆盖 CCGS 12 个 Hook 的大部分场景。主要差异：CodeBuddy **不支持** SubagentStart/SubagentStop（无法直接移植 log-agent.sh / log-agent-stop.sh）；也无 PostCompact 和 Notification 事件；Hook 脚本支持 Python，不限于 Bash |
| **Path-Scoped Rules（11 条）** | 改造移植 | CodeBuddy Rules 支持"总是/智能体请求/手动"三种加载模式，但**不支持 glob 路径作用域**（CCGS 的路径作用域是 Claude Code 的特有机制）；需改为"手动规则 + `@my-rule` 显式引用"的方式，或写入 CODEBUDDY.md 全局生效 |
| **上下文管理策略** | 直接移植 | 文件即记忆、增量写入、主动压缩（`/summarize`）均是通用最佳实践，CodeBuddy 完全支持；`/summarize` 对应 CCGS 的 `/compact` |
| **目录结构约定** | 直接移植 | 纯文件系统约定，与平台无关；只需将 `.claude/` 对应改为 `.codebuddy/` |
| **CODEBUDDY.md 主入口** | 直接移植 | CodeBuddy 原生支持项目根目录的 `CODEBUDDY.md`（全文加载）；同时兼容 `AGENTS.md`。CCGS 的 `CLAUDE.md` 可直接改名复用 |
| **三引擎支持架构** | 直接移植 | 引擎专员组的分工思路可复用；具体内容可选择单引擎子集 |
| **CCGS Skill Testing Framework（元测试）** | 改造移植 | 测试思路有价值；执行需改为 CodeBuddy Skills（`.codebuddy/skills/`）替代 Claude Code 的斜杠命令 |
| **编码与设计标准（coding-standards.md）** | 直接移植 | 纯文本规范，可直接放入 CodeBuddy Rules（alwaysApply: true）全局生效 |
| **状态栏脚本（statusline.sh）** | 不建议移植 | 依赖 Claude Code 专有的 `statusLine.command` 配置；CodeBuddy 无对应 UI 扩展点，暂无移植路径 |

### 关键差异速查（直接影响移植决策的 5 个要点）

| 要点 | CCGS / Claude Code | CodeBuddy 实际情况 |
|---|---|---|
| **并行 Subagent** | 支持（多个 Task 同时 spawn） | **不支持**，当前只有串行 agentic 模式 |
| **SubagentStart/Stop 事件** | 支持（用于 audit trail） | **不支持** |
| **Rule 路径作用域（glob）** | 支持（`src/gameplay/**` 等） | **不支持**，Rules 按加载模式触发，无路径过滤 |
| **Memory 分级（user/project）** | 支持两级 | 只有全局 Memory，项目级需用 Rules 替代 |
| **配置目录** | `.claude/` | `.codebuddy/`（格式高度兼容） |
